## 0 结论先行

- 要做的是一件**只读台账**：专栏新增 `/sources` 总览与 `/sources/<slug>` 详情，把飞书「信源表_v2.0」的 **104 行 × 31 字段**完整搬到站内。
- 不是法规知识库，不是编辑后台，不是公开 API。
- 唯一的硬指标是**完整性**：31 个字段一个不少、104 行一条不缺。读者不打开飞书，就能回答「这条法规现在什么状态、什么时候实施、原文在哪、跟我们做的功能什么关系」。

## 1 第一性原理

连问三层，把"要一个页面"还原成真实约束。

**① 这张表到底是什么？**

它是 regpilot 维护的**法规台账**，一行 = 一部法规 / 测评规程，31 列按语义分七组：

| 组 | 字段 | 回答的问题 |
|---|---|---|
| 身份 | 法规编号、法规全称 | 这是哪一部 |
| 归属 | 地区、适用国家、适用车型 | 管哪些国家、哪些车 |
| 分类 | 业务分类、产品功能、法规认证类型 | 归我们哪条产品线、强制还是推荐 |
| 时间 | 发布日期、实施日期、修订日期、征求意见截止、报批稿截止、上次检查日期 | 什么时候生效、还来不来得及 |
| 来源 | 信源T1-官方、信源T2-行业、信源T3-资讯、原文链接、印证状态、印证策略 | 依据在哪、可不可信 |
| 处理状态 | 生命周期阶段、原文入库、原文获取方式、订阅状态、解读状态 | 我们跟到哪一步了 |
| 内容与人 | 核心摘要、影响评估、认领人 | 对我们意味着什么、谁负责 |

> 这里是**数据分析用**的语义分组；页面呈现按 02 §3.2 的 8 节（身份与归属 / 分类 / 关键日期 / 来源与可信度 / 处理状态 / 内容 / 人员 / 其他字段）。两处只是分析视角不同，字段一个不少。

**② 谁在用它、用它做什么？**

| 角色 | 具体问题 | 现在怎么做 | 卡在哪 |
|---|---|---|---|
| 法规工程师（主） | 这条法规现在什么状态？什么时候实施？有没有征求意见？ | 打开飞书表逐行找 | 104 行，找一条要滚很久 |
| QA | 我们要测的功能受哪些法规约束？ | 用飞书筛选业务分类 | 筛选要记住字段名；组合筛选难 |
| 产品 / 算法 | 疲劳检测、DMS 这些功能被哪些法规点名？ | 靠印象或问人 | 没有"按功能反查法规"的入口 |
| 管理者 / 新同事 | 我们到底在盯多少法规、覆盖哪些地区？ | 无 | 缺少全貌 |

**③ 为什么现在在飞书里不够？** 三个具体摩擦，不是"想要个网页"：

1. **找得慢**：104 行 × 31 列，飞书表格在手机上基本没法看。
2. **筛得浅**：飞书筛选是字段级的，做不了"功能 × 地区 × 生命周期"这种组合，也不能把结果发给别人复现。
3. **传不出**：把链接发给不用飞书的同事，对方打不开。

**由此得出需求的本体**：把台账**完整**搬到读者面前，并把检索成本降下来。凡是超出这个范围的（编辑、解读、问答、原文库），都属于别的阶段，见 §4.2。

## 5 数据完整性的定义（硬约束）

这三条既是需求，也是验收和测试的口径：

1. **字段完整**：31 个字段全部在详情页可见；源表出现规范外字段时进「其他字段」，不丢。
2. **行完整**：一次成功同步后，站内行数 = 飞书表行数（当前 104）。差异必须能被解释（删除的行、分页没取全）。
3. **只删于完整之后**：只有当一轮同步**全部成功**后才允许删除飞书侧已消失的行；任何一步失败，整轮不写，页面上仍显示上一版与它的同步时间。

## 6 与现有功能的关系

| 现有 | 关系 |
|---|---|
| 专栏「法规追踪」`/regulations` | **并存**（使用者 2026-11-17 定）。它是按分类筛资讯的动态流，本页面是台账；两者互不替代 |
| 法规模块 `modules/regulation/` | 独立。它管「90 天内到期的日期」与日报倒计时块，数据来自人工整理的 `regulation_schedule`；本期不合并 |
| 飞书投影 `FEISHU_BITABLE_*` | **无关**。那是门户 → 飞书写，方向相反；本期是飞书 → 门户读 |
| 信源管理 `/admin/sources` | 无关。那是采集信源（RSS 等），本表是法规台账，同名不同物 |
