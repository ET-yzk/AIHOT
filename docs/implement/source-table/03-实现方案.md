# 信源表页面 — 实现方案

| 项 | 值 |
|---|---|
| 需求 | 把「车载法规信源记录表」（飞书多维表格）搬成站内页面：总览可查可筛可排，每条可点进详情 |
| 数据源 | Base `VBcRbUgETasPxdsBHOEcbT0wndd` / 表 `tblMHJCpipvyRaNJ`（信源表_v2.0），实测 104 条 × 31 字段 |
| 落点 | `modules/source-table/`，npm 包 `@aihot/source-table` |
| 形态 | 入站同步（飞书 → Postgres）+ 只读页面；与出站的 `FEISHU_BITABLE_*` 投影是两件相反的事，不复用变量 |
| 状态 | 待评审 |

## 0. 结论

三步：**worker 定时把整张表拉进 Postgres**，**两个只读接口**，**两个页面**。数据只在同步时进库，页面永远读库，读者打开页面不产生任何外部请求。

| 决定 | 选择 | 为什么不选另一个 |
|---|---|---|
| 数据通道 | worker 拉取（pull） | regpilot 推送要改 WSL 侧、还要给站点开口令；手工快照只作权限未通时的兜底 |
| 落库形状 | 31 个字段各占一列 + `raw jsonb` 全量备份 | 只存 raw：筛选排序要么全表扫内存，要么每加一个筛选条件写一次 JSON 表达式；只存列：飞书以后加的字段会静默消失 |
| 写入时机 | 一轮抓完、全部成功才在一个事务里写 | 边抓边写会在中途失败时留下半份数据，页面看不出是半份 |
| 页面形态 | 桌面表格 + 手机卡片 + 独立详情页 | 主从分栏的右侧预览不适合 31 个字段；详情页本来就要做 |
| 索引 | 先不建 | 104 行顺序扫比走索引快；建索引要单独一条 `CONCURRENTLY` 迁移，等真的需要 |
| 详情页收录 | `noindex` | 内网台账，进搜索引擎没有收益，还会把内部口径暴露给爬虫 |

## 2. 数据库

### 2.1 建表（`modules/source-table/migrations/0152_source_table_rows.sql`）

从 0055 起一个迁移文件只放一条允许在线执行的语句，所以这里只有一条 `CREATE TABLE`；索引、回填各自另开文件。

```sql
-- 信源表（飞书多维表格「信源表_v2.0」）在站内的只读镜像。
-- 整轮抓取成功后由 modules/source-table/sync.ts 在一个事务里重写；页面只读这张表。
-- 31 个业务字段各占一列（筛选、排序用），raw 留整条记录的原文（飞书以后加的字段不丢）。
-- 104 行，顺序扫描比走索引快，先不建索引；表长到需要时，另开一个迁移写 CREATE INDEX CONCURRENTLY。
CREATE TABLE IF NOT EXISTS source_table_rows (
  record_id            text PRIMARY KEY,
  slug                 text NOT NULL UNIQUE,
  code                 text,
  title                text NOT NULL,
  region               text,
  lifecycle            text,
  business_categories  text[] NOT NULL DEFAULT '{}',
  product_functions    text[] NOT NULL DEFAULT '{}',
  cert_type            text,
  publish_org          text,
  apply_countries      text[] NOT NULL DEFAULT '{}',
  vehicle_types        text,
  published_on         date,
  revised_on           date,
  effective_on         date,
  comment_deadline     date,
  report_deadline      date,
  origin_url           text,
  archived_state       text,
  origin_mode          text,
  corroboration        text,
  corroboration_policy text,
  subscription_state   text,
  interpretation_state text,
  owners               text[] NOT NULL DEFAULT '{}',
  summary              text,
  impact               text,
  source_t1            text,
  source_t2            text,
  source_t3            text,
  checked_on           date,
  created_on           date,
  updated_on           date,
  raw                  jsonb NOT NULL,
  synced_at            timestamptz NOT NULL DEFAULT now()
);
```

### 2.3 为什么有 `raw jsonb`

三条理由，都不是推测：

1. **字段会加。** 附录 B 记着这张表从 62/71/72 涨到 73 条，实际现在已 104 条；字段数也从 29 涨到 31。飞书加一列，页面不该跟着发一次迁移。
2. **值会漂。** 实测「业务分类」出现了文档 8 项之外的「底层」。枚举不写死，取值从数据里来，原文留在 `raw` 里可以追溯。
3. **排障要对照。** 页面显示和飞书不一致时，`raw` 是唯一能逐字段比对的东西。

代价：一条记录的 raw 约 2 KB，104 行不到 250 KB。页面渲染用的是列，`raw` 只在详情页的「其他字段」一节和排障时读。

### 2.4 为什么不先建索引

104 行，一页最多 50 条，顺序扫是微秒级。`CREATE INDEX CONCURRENTLY` 必须单独一个迁移文件（一条语句的约定），且索引要能被规划器用上才有意义。触发条件写清楚：**表超过 1 万行，或 `pg_stat_statements` 里这条列表查询进入慢查询**，再另开迁移建 `(lifecycle, region)` 与 `(updated_on DESC)`。

### 2.5 回退

不预先提交 DROP 迁移（提交了就会执行）。回退时新增一个迁移，**编号取提交当时的下一个可用号**（写成 `n_drop_source_table_rows.sql`，例如当前是 `0152` 之后就用 `0153`；M1–M5 期间若有别的迁移落地，回退时顺延，避免撞号）：

```sql
DROP TABLE IF EXISTS source_table_rows;
```

不带 `CASCADE`：没有其他对象依赖这张表。按 `docs/architecture.md`，删表要同步删代码、测试与配置，并在 `docs/deploy.md` 的更新说明里写明对已有数据的影响（这张表可以重建，重新同步即可，没有不可恢复的数据）。

## 3. 同步（`sync.ts`）

### 3.1 开关与凭据

| 变量 | 读法 | 默认 | 作用 |
|---|---|---|---|
| `SOURCE_TABLE_SYNC_CRON` | `credential("integrations", …)` 或 config 字符串，默认 `0 */6 * * *` | 6 小时 | 同步频率；调度器与页脚文案都读它，改频率不改代码 |
| `FEISHU_SOURCE_TABLE_WEB_URL` | config 字符串 | 空 | 页脚「数据源」链接，**人能直接打开的那一条**：`https://arcsoft.feishu.cn/wiki/FVLOwrEWziJLWokvcd0cSP8Lnce?table=tblMHJCpipvyRaNJ`。它含知识库节点 token，**无法由 app_token 拼出**（`/base/<app_token>` 是给 API 用的地址），所以单独存一个 key；为空时页脚只显示「数据源：飞书「信源表_v2.0」」，不出链接 |
| `SOURCE_TABLE_SYNC_ENABLED` | `config.sourceTableSyncEnabled`（在 `packages/backend/src/config.ts` 加 `sourceTableSyncEnabled: bool("SOURCE_TABLE_SYNC_ENABLED", false)`） | 关 | 关着时不发任何 HTTP，只记水位 `disabled`。**与 `projection/bitable.ts` 同一写法：读 config，不直读 `process.env`**（`config.ts:60` 的 `feishuBitableEnabled` 就是范例） |
| `FEISHU_SOURCE_TABLE_APP_TOKEN` | `credential("integrations", …)` | 空 | Base 的 app_token，实测 `VBcRbUgETasPxdsBHOEcbT0wndd` |
| `FEISHU_SOURCE_TABLE_TABLE_ID` | `credential("integrations", …)` | 空 | 表的 table_id，实测 `tblMHJCpipvyRaNJ` |

开关先答，凭据后答：开关关着返回 `disabled`，开着但缺凭据返回 `unconfigured`。

**不复用 `FEISHU_BITABLE_APP_TOKEN` / `FEISHU_BITABLE_TABLE_ID` / `FEISHU_BITABLE_ENABLED`。** 那三个是出站投影（门户精选写进飞书表）的目标，方向相反；混用之后要么开入站顺手改了出站的目标表，要么哪天关掉投影把入站一起关了。

### 3.2 抓取

1. `await tenantToken()`（复用 `@aihot/backend/notify/feishu` 的 `tenantToken` 与 `API`）。
2. `GET /bitable/v1/apps/{app}/tables/{table}/fields` 一次，拿到每个字段的真实类型（`select` 是否 `multiple`、`datetime`、`user` 等）。失败即整轮失败——类型猜错会把多选当单选写坏。
3. `POST /bitable/v1/apps/{app}/tables/{table}/records/search`，`{"automatic_fields": false}`，`page_size: 500`，按响应的 `page_token` 翻页直到 `has_more === false`。
4. 页数上限 50 页（2.5 万行）。超过就报错退出，不静默截断——截断后再删行等于删数据。
5. 每条请求 30 秒超时（与投影一致），失败重试 2 次、指数退避；仍失败整轮失败。

### 3.2.1 真实返回值的形状（2026-11-17 用应用自己的 token 实测）

不要按文档想象字段类型，飞书返回的形状是固定的：

| 飞书字段类型 | 实测样本 | 取值方式 |
|---|---|---|
| 文本（type 1，11 个） | 法规全称、核心摘要、影响评估、发布机构、适用车型、信源 T1/T2/T3、印证策略、法规编号 | 返回的是**富文本数组** `[{ text, type }]`：取 `arr.map(s => s.text).join("")`，不要直接当字符串用 |
| 单选（type 3，8 个） | 地区、生命周期阶段、法规认证类型、原文入库、原文获取方式、印证状态、订阅状态、解读状态 | 直接是字符串 |
| 多选（type 4，3 个） | 业务分类、产品功能、适用国家 | 字符串数组 |
| 日期（type 5，6 个） | 发布日期、实施日期、修订日期、征求意见截止、报批稿截止、上次检查 | **毫秒时间戳**数字，按 Asia/Shanghai 换算成 YYYY-MM-DD |
| 人员（type 11，1 个） | 认领人 | 用户对象数组（`id`/`name`），104 条当前全空 |
| 创建/更新时间（1001/1002） | — | 毫秒时间戳，只读 |

`原文链接` 是**超链接字段**，返回 `[{ link, text, type }]`：优先取 `link`；没有 `link` 时才回落到解析 `text` 里的 Markdown（§3.4）。这比原先只认 Markdown 稳，因为飞书把 Markdown 文本也存进了 `text`。

### 3.3 字段映射

值有两种形态，都要吃：多维表格 OpenAPI 对 `datetime` 返回**毫秒时间戳**，`select` 单选返回字符串、多选返回数组，`user` 返回 `[{id,name}]`。`lark-cli` 导出的 ndjson 里看到的是 ISO 串，那是工具转换过的，不能只按它写。

| 飞书类型 | 映射规则 |
|---|---|
| text（富文本数组） | `arr.map(s => s.text).join("")` 再 trim；空串视为 `null`。**不能直接当字符串用**，实测 11 个文本字段全是这个形状 |
| select（单选） | 字符串；空数组/空串视为 `null` |
| select（多选） | `string[]`，去空、去重、保持原顺序；空数组写 `'{}'` |
| datetime | 数字 → `beijingDate(new Date(n))`（`@aihot/contracts/time`）；已是 `YYYY-MM-DD` 前缀的字符串 → 取前 10 位并校验；其余 → `null` |
| user | `[{name}]` → `string[]` 的显示名 |
| 未知类型 | 不猜，原样留在 `raw`，详情页进「其他字段」 |

**日期一律不自己做时区换算。** 权威换算只在 `packages/contracts/src/time.ts`，仓库有一条检查盯着这件事（`tests/architecture.test.ts` 的「Beijing time is converted only in contracts/time.ts」）；同步里出现手写的偏移量或时区拼接会让它变红。

### 3.4 Markdown 链接解析

实测「原文链接」的 `text` 里是 `[中汽测评|C-NCAP 技术规程](https://…)` 这种 Markdown，但**用应用自己的 token 读 API 时，104 条全部带 `link` 字段**（2026-11-17 实测 104/104），所以优先取 `link`，Markdown 解析只作兜底（导出文件、以后手填纯文本时用）。解析规则：

```
^\[([^\]]*)\]\(\s*(https?://[^\s)]+)\s*\)$   → { url, label }
^https?://\S+$                                  → { url, label: null }
其余                                             → { url: null, label: 原文 }   // 原文留在 raw
```

`origin_url` 只存可点的 `http(s)` 地址；解析不出地址时留空，详情页照原文文字显示并标注「不是可点链接」。「信源T1-官方」这类字段同理，但只做展示，不拆成结构化。

### 3.5 slug

```
slug = (code ?? "reg-" + record_id)
         .normalize("NFKC").toLowerCase()
         .replace(/[^a-z0-9]+/g, "-").replace(/^-+|-+$/g, "").slice(0, 80)
```

- 中文编号经 NFKC 后可能被全部替换掉，结果为空 → 回落 `reg-<record_id>`。
- 冲突（`CNCAP-2024` 与 `cncap 2024` 归一后相同）：按 `record_id` 升序稳定排序，第二个起加 `-2`、`-3`。**排序固定，所以同一份数据每次同步算出的 slug 都一样。**
- **已存在的 `record_id` 保留原 slug。** 编号在飞书里被改正时不换网址，旧链接不会 404。

### 3.6 写入

一个事务，四步，任何一步失败整轮回滚：

```sql
-- 0) 互斥：cron 与手工脚本可能同时跑（§3.8 提供了入口），事务级咨询锁让后来者排队而不是死锁
SELECT pg_advisory_xact_lock(hashtext('source-table.sync'));

-- 1) 先删后写。顺序反过来会永久卡死：一条记录在飞书里被删、同时新增一条编号恰好等于它旧 slug 的记录时，
--    INSERT 会撞上「即将被删但还没删」的行的唯一约束，整轮回滚；下一轮那行还在，于是每 6 小时失败一次。
DELETE FROM source_table_rows WHERE record_id <> ALL(${ids});

-- 2) 分批 upsert，每批 500 行。35 列 × 500 ≈ 17500 个绑定参数，离 Postgres 的 65535 上限还有余量；
--    不批量的话按 §4.2 允许的 50 页 × 500 条会直接撞上限（约 1872 行即失败）。
INSERT INTO source_table_rows (…35 列…) VALUES <500 行>
ON CONFLICT (record_id) DO UPDATE SET <除 record_id 外的每一列> = EXCLUDED.<同名列>, synced_at = now();
```

先删后写在同一事务里语义等价：删除条件是「本轮没取到的 record_id」，与 upsert 的目标集合不相交。

守卫两条，都有明确依据：

- **抓到 0 条不写、不删**，记 `failed`。表被改名、权限被撤、字段全空都可能返回 0 条，这时按「同步成功」删光是最坏的结局。需要清空时人工跑 `scripts/sync-source-table.ts --allow-empty`（见 §3.8），并记 `removed: N`。
- **落库前按 `record_id` 去重，并核对取回条数 ≥ 首页响应的 `total`。** 翻页期间有人在飞书里删行，`page_token` 会跳过一条；那条不在 `ids` 里就会被当成「已删除」删掉，而整轮还报成功。接口给了 `total`，用它校验比设阈值有依据。

不做「条数掉一半就拒写」这类阈值：没有任何证据说明它会发生，先不加。

### 3.7 水位

写 `settings` 表（已存在：`key text PRIMARY KEY, value jsonb, updated_by, updated_at`），键 `source-table.sync`：

```json
{ "status": "ok|failed|disabled|unconfigured", "at": "2026-11-17T09:30:00.000Z",
  "lastOkAt": "2026-11-17T09:30:00.000Z", "rows": 104, "created": 0, "updated": 3, "removed": 0, "error": "…",
  "runs": [ { "at": "2026-11-17T09:30:00.000Z", "ok": true, "rows": 104 },
            { "at": "2026-11-17T09:00:00.000Z", "ok": false, "rows": 0, "error": "99991672 …" } ] }
```

失败也写：只把 `status` 与 `error` 换掉，`error` 之外与成功时同形。`at` 是本轮时刻，**`lastOkAt` 只在 `status="ok"` 时更新**，页面用它显示「上次成功 09:30」而不是假装数据是新的。`updated_by` 写 `"worker"` 或 `"script"`。

## 4. 读取层与接口

### 4.0 与公开读取层（`publication/`）的关系

仓库规则是「所有公开出口都从 `packages/backend/src/publication/` 这一个读取层读」。这条规则**约束的是新闻与事件内容**：它承载公开范围、精选席位、事实证据条件与**撤回**语义（`publication/scope.ts`）。信源表是参考数据，不是内容：

| | `publication/`（新闻与事件） | 本模块（法规台账） |
|---|---|---|
| 谁决定一条能不能看 | `scope.ts` 的谓词（公开范围、撤回、全文许可） | 不适用：飞书表里有的就是能看的，**没有撤回状态** |
| 数据形态 | 采集来的文章、事件、报告 | 人工维护的参考台账，单向入站 |
| 读者可见性 | 匿名，但与内容治理耦合 | 匿名，与内容治理无关 |

因此读取函数留在模块自己的 `read.ts`，与 `modules/subscriptions`（读者个人的订阅页）同一个形态。**这条边界要写进 `docs/architecture.md`**：把「网页」那半句限定为「新闻与事件内容」，否则下一个人会照着旧措辞问同样的问题（见 04 的 P12）。

### 4.2 列表 `GET /api/site/source-table`

| 参数 | 形态 | 说明 |
|---|---|---|
| `q` | 字符串，≤200 | 搜索编号、全称、摘要、发布机构；多词 AND；中英文拆分复用 `publication/pool.ts` 的 `searchTerms` |
| `region` `lifecycle` `business` `function` `cert` `org` `archived` `subscribed` | 可重复的键（`?business=DMS&business=OMS`） | 同组内 OR（数组列用 `&&`），跨组 AND；值不在数据里就当没传，不报错 |
| `sort` | `updated`（默认）`published` `effective` `code` | 见 4.4；其他值 400 |
| `page` | 1 起 | 超出按最后一页返回 |
| `pageSize` | 15（默认）/ 30 / 50 | 其他值 400；104 行下 15 条 → 7 页 |

响应头：`sendJsonWithEtag(req, reply, body, { etagPrefix: "st", cacheControl: "public, max-age=60, s-maxage=60" })`，并在发送前设 `X-Accel-Expires` 为绝对截止时间——与 `/api/site/pool` 同一个写法，好让 `cachedPage` 取到同一个上限。

`syncedAt`、`lastOkAt`、`syncStatus` 与列表数据在同一个响应里，页面不会出现「总数更新了但时间没更新」。

同一个响应还带两样东西给页脚：

- `recentRuns`：最近 5 次同步（`at`、`ok`、`rows`、`error?`），来自水位里的 `runs`（§3.7）。页脚圆点悬停时显示它，**不额外发请求**。
- `cron` 与 `everyLabel`：同步频率（`SOURCE_TABLE_SYNC_CRON`）。「每 6 小时」由页面按 cron 推导，不写死在文案里。

### 4.3 详情 `GET /api/site/source-table/:slug`

- slug 校验 `^[a-z0-9-]{1,80}$`，不合法直接 404（不查库）。
- 查不到 404，用 `sendProblem`（`code: "not_found"`），页面侧 `loadOr404` 转成标准错误页。
- `fields` 的顺序固定：内容 → 日期 → 范围 → 分类 → 原文 → 信源 → 维护，每组内按 2.2 表里的顺序。
- `meta: true` 的字段（信源 T1/T2/T3、印证状态与策略、原文入库、获取方式、订阅状态、解读状态、认领人、上次检查、创建时间、更新时间，共 13 项）渲染进详情页底部的折叠区；其余进主体。若全部折叠字段都为空，折叠区仍显示，只是内容为「—」。
- 分组 key 到页面节标题的对照（与 02 §3.2 的线框一致）：内容→「摘要与影响」、日期→「关键日期」、范围→「适用范围」、分类→「分类与功能」、原文→「原文」；`meta` 的字段按 `metaGroup` 分进「元数据 · 信源与维护信息」折叠区的两组；`extra` 非空时追加「其他字段」。

### 4.4 排序与空值

| `sort` | SQL | 语义 |
|---|---|---|
| `updated` | `updated_on DESC NULLS LAST, code ASC` | 默认，最近动过的在前 |
| `published` | `published_on DESC NULLS LAST, code ASC` | 新发布的在前 |
| `effective` | `effective_on ASC NULLS LAST, code ASC` | 快实施的在前（读者问的是「我什么时候要合规」） |
| `code` | `code ASC NULLS LAST, title ASC` | 查具体编号 |

四种都带第二排序键，让翻页结果稳定（同一页刷新不会重排）。

### 4.5 筛选项聚合

一次 `UNION ALL` 查询算全部八组，避免八次往返：

```sql
SELECT 'region' AS kind, region AS value, count(*)::int FROM source_table_rows WHERE region IS NOT NULL GROUP BY 2
UNION ALL SELECT 'lifecycle', lifecycle, count(*)::int FROM source_table_rows WHERE lifecycle IS NOT NULL GROUP BY 2
UNION ALL SELECT 'business', b, count(*)::int FROM source_table_rows, unnest(business_categories) AS b GROUP BY 2
UNION ALL SELECT 'function', f, count(*)::int FROM source_table_rows, unnest(product_functions) AS f GROUP BY 2
UNION ALL SELECT 'cert', cert_type, count(*)::int FROM source_table_rows WHERE cert_type IS NOT NULL GROUP BY 2
UNION ALL SELECT 'org', publish_org, count(*)::int FROM source_table_rows WHERE publish_org IS NOT NULL GROUP BY 2
UNION ALL SELECT 'archived', archived_state, count(*)::int FROM source_table_rows WHERE archived_state IS NOT NULL GROUP BY 2
UNION ALL SELECT 'subscribed', subscription_state, count(*)::int FROM source_table_rows WHERE subscription_state IS NOT NULL GROUP BY 2
ORDER BY 1, 3 DESC;
```

筛选项跟着整张表走，不跟着当前结果走：这样 chip 列表稳定，选了中国之后其他地区不会被挤掉。

**计数只用来给 chip 排序（多的在前），不显示在界面上。** 显示「中国 58」而当前查的是「征求意见稿」会误导读者，要算「换成中国还有多少条」就得按当前条件重算八组聚合，复杂一个数量级，需求（FR-ST-03/05）也没要求。

| 加载态 | `useNavigation().state === "loading"` 时给结果区 `opacity-50`，与 `/all` 一致 |
| 列选择 | 本机记住（`lib/local-state.ts` 加一个 `source-table.columns` 键），默认列：编号、全称、地区、生命周期、业务分类、发布日期、实施日期、更新时间 |

| 四态 | `syncStatus="never"` → 「还没同步过」+ 管理员可见的执行命令；`"disabled"` → 「同步未开启」，页面照常显示上次数据；`"unconfigured"` → 「应用未配置」并给出缺的变量名；`"failed"` 只在页脚条显示（红点 + 「本次同步失败 · 上次成功 X」），**不弹横幅**；→ 黄条 + `lastOkAt`；`"ok"` 但结果为空 → 「换个条件」+ 清除筛选 |

| 返回 | 页首放「‹ 返回法规信源」（与 02 §3.2、Demo 一致，满足 FR-ST-09 的「返回保留筛选」）；筛选在 URL 里，浏览器后退同样恢复。两者不冲突 |
| 其他字段 | `extra` 非空时在最末渲染一节「其他字段」，注明「来自飞书原表」 |

### 5.3 导航

`web.tsx` 声明 `sidebar.section = "专栏"`，`nav.ts` 的 `sidebar()` 会把这一项追加到 `modules/columns` 已经建好的「专栏」分区末尾，得到：法规追踪、标准解读、NCAP 评测、车企动态、**法规信源**。手机底栏不变，「我的」页不变。

按仓库要求，导航改动要在浏览器里逐项核对：默认配置下的电脑侧栏、`NAV.hidden` 非默认配置下的侧栏、`wide` 宽度以下的 rail、`lg` 以下的手机视图、以及新增项在深色主题下的对比度。

## 9. 上线与回滚

### 上线

1. 飞书侧：站点应用开通 `bitable:app:readonly` → 创建版本并发布 → 管理员审批 → Base「协作者」里加该应用为「可阅读」→（Base 在知识库里时）知识库「成员」里也加一次。
2. 部署新镜像；`setup` 自动执行 `0152`。
3. `.env` 填三项：`SOURCE_TABLE_SYNC_ENABLED=true`、`FEISHU_SOURCE_TABLE_APP_TOKEN=VBcRbUgETasPxdsBHOEcbT0wndd`、`FEISHU_SOURCE_TABLE_TABLE_ID=tblMHJCpipvyRaNJ`（后两个是实测值，换表时改）。
4. 重启 api 与 worker。
5. 首次同步：`node --env-file=.env scripts/sync-source-table.ts`，看输出 `rows=104`；不等它也最多 6 小时。
6. 核对：`/sources` 条数 104；抽 5 条与飞书原表对字段；`settings['source-table.sync'].status = ok`。

### 回滚

| 情况 | 动作 |
|---|---|
| 页面有问题 | 从 `site/modules/{index,server,web}.ts` 删掉模块、`site/package.json` 删依赖、Dockerfile 删 COPY 行，重新部署。页面与接口一起消失，表和数据保留 |
| 同步把数据写坏 | `SOURCE_TABLE_SYNC_ENABLED=false` 重启 worker，页面停在最后一次水位；修好后手工跑脚本 |
| 彻底不要了 | 先按上一条下线，确认不再需要，再提交 `0153_drop_source_table_rows.sql`；在 `docs/deploy.md` 写明删了什么、重建方式（重新同步即可） |

页面下线不影响站点其他部分：模块只在三份清单里被引用，框架本身不认识它。

## 10. 不做

| 不做 | 原因 |
|---|---|
| 站内编辑、写回飞书 | 单向入站是这套设计的地基；写回会引入冲突合并与权限问题 |
| 认领人、解读状态流转 | 表里「认领人」104 条全空、「解读状态」只有 2 条已沉淀；等真有认领动作再设计 |
| 原文库、PDF 上传与解析 | 属于需求文档阶段三，另立模块 |
| FAQ 归档、不关注清单、分类表、信源表_v1.0 | 本期只做信源表_v2.0（104 条）；另 5 张表目标形态未定 |
| 公开 API、RSS、MCP、sitemap 出口 | 内网台账，详情页 `noindex`，不进任何机器出口 |
| 按角色的字段遮蔽 | 站点没有角色体系（FR-09-07 未排期）；本次全部字段对匿名访客可见，是内网口径下的决定 |
| 主从分栏的右侧预览 | 详情页已经是独立页面，预览是重复实现 |
| 条数骤降阈值、同步失败告警 | 没有证据说明会发生；先只守「抓 0 条不删」这一条有明确风险的 |
| 为 104 行建索引 | 顺序扫更快；等表大了再单独迁移 |
