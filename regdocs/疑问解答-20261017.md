## 1. regpilot 导入的信源是一次性的吗？现有信源以后还会盯到更新吗？

分两半看，答案不一样：

- **语料是一次性的。** `backfill-regpilot` 那条源 kind 是 `external`，`packages/backend/src/sources/collect.ts:107` 对 `external` 直接跳过（注释：external sources only receive reports）——它只接收推送（`POST /api/ingest/items`），从不轮询。那 79 条历史就是一次性导入的存量，以后不会自己长。
- **信源是常驻的。** `industry/sources.json` 里的发布机构（工信部、C-NCAP、Euro NCAP…）由 `scripts/seed.ts` 只插一次（`ON CONFLICT (id) DO NOTHING`，不会覆盖你在后台改过的），但采集器按各自间隔**一直轮询**：worker 每分钟挑到期的源（`collect.ts:364`），`adaptIntervals` 每天按产出量把间隔调到 active 15 分钟 → quiet 120 分钟（`collect.ts:383-397`，热点/X/付费源上限更高）。所以这些机构的后续更新会一直盯到。
- **清单之外的机构不会自动被盯。** 要新增得写进 `industry/sources.json` 再 seed，或让 RegPilot 走 ingest 接口推。

## 2. 主题页的主题是动态更新还是写死的？

清单写死、内容动态：

- **清单**（slug / 名字 / 分组 / 定义 / 实体 / 别名 / 标签）在 `industry/topics.json`，`packages/backend/src/publication/topics.ts:54` 在进程启动时读一次。加/改主题要改这个文件并重启 api 与 worker，**不会自己长出来**。
- **主题下的条目与计数**是每次读库现算的（`topicMembership` / `loadTopicPage` / `currentSeats`），新文章发布后自动出现在对应主题下。
- **归属**靠文章分析时模型打的实体标签（`entity:<id>`）；公司类主题还要求标题里出现该公司名（或它是唯一主体），见 `topics.ts` 的 `titlePattern`。

## 4. 当前站点支持 LLM 回退策略吗？

**不支持「主模型失败自动切备用模型」。** 每个步骤（capability）用一个模型，来源优先级是 **后台「模型」页设置 → 环境变量（`SCORE_MODEL` 等）→ `site/models.ts` 的代码默认**（`packages/backend/src/editorial/models.ts:86`，未知名字回落默认）。失败的处理是**重试**（`jobs/content.ts` 的 `RETRY_MINUTES` 指数退避 + `content.sweep`）和**预算熔断**（`providers/receipts.ts`），不是换模型。想「回退」只能手动：后台改（60 秒缓存后对新调用生效）或设环境变量。

## 5. 上游同步是怎么个协作工作流？为什么是「被覆盖」而不是「冲突」？

- **远端。** `origin` = 你的 fork `ET-yzk/AIHOT`；`upstream` = `KKKKhazix/AIHOT`（只读）。同步 SOP 走**本地 `main`**：`fetch` → `main` 快进到 `upstream/main` → 在 `dev` 上 `merge --no-ff main` → 打 `pre-sync-*` 回滚锚点 → 冲突按 `FORK-CHANGES.md` 的清单核 → 跑门禁。首次按这套跑通是 `25ea05c`（2026-10-15）。
- **为什么不直接 rebase。** 早期是 rebase/cherry-pick，但 `merge --no-ff` 之后 `dev-synced` 那条线并进来、主线改 `dev`（`ffc09cc`），同步就固定成上面这套。
- **你说的「要么冲突手动合、要么不冲突」对已提交的改动基本成立。** 项目记的三次事故（「主题与品牌」「Mimo 主题」「2026-10-12 两处」）是另一种形状：同步**把 fork 侧已定过的改动还原成了上游的样子**——不是 git 报冲突，而是那段改动被上游版本盖掉（改的时候还没提交，或同步按上游的文件内容落）。所以规矩是：**改上游文件就要提交，并把每个改过的上游文件登记进 `FORK-CHANGES.md`**，同步后逐条核对。`check-fork-changes-coverage.mjs` 就是把这条规矩变成机器检查。
- **所以「为什么会被覆盖」的答案**：不是 merge 冲突那一类，是「上游提交重写了同一个文件 + 改动没提交或没登记」这一类**静默丢失**。提交 + 登记 + 每次同步后核对，三条一起才是防护。
