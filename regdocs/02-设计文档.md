## 0 设计前提：核验纠正

调研过程中发现的关键事实，直接改变了设计策略。

| # | 纠正 | 证据 | 设计后果 |
|---|---|---|---|
| V1 | **声明式采集能力比预期大得多，不必自带爬虫** | `AIHOT/packages/backend/src/sources/json-list.ts` 实现 `mode: html_window_var / html_json_key`（平衡括号扫描器）、`method`+`headers`+`bodyJson`、`publishedAtUnit: epoch_ms` | C-NCAP 的 POST 接口、MIIT 的 13 位日期、SAC 内联 blob 都可能是**配置**。需真实浏览器的只剩 EUR-Lex 与 IVISTA/CATARC，做成外部推送器（§7） |
| V2 | **`allowUrlPrefixes`/`denyUrlPrefixes` 只在 `web-list.ts` 生效** | `sources/config-keys.ts:7` 注释称"由 `collect.ts` 对所有 kind 生效"；实测 `collect.ts` 从不读 | 列为开工前置修复；在它修好前不得作为唯一围栏 |
| V3 | **生产启动会拒绝内网访问开关** | `config.ts:100` 在 `ALLOW_PRIVATE_NETWORK_FETCH=1` 时拒绝启动；`lib/http-fetch.ts:33-36` 做 SSRF 检查 | 调局域网知识层必须走窄口径白名单 + 独立 dispatcher（`route:"direct"`），**不开全局开关**（§9.6） |
| V4 | **AIHOT 完全没有这些能力**（本次的新增面） | 无生命周期状态机 / 无评审队列 / 无排除清单 / 无文档库（`stored_files` 无任何写入方）/ 无查询期 RAG / 无飞书写回 | 这些是真正的新代码，以模块形式接入 |
| V5 | **两套向量平面必须刻意隔离** | AIHOT 侧 `qwen3-vl-embedding-8b`/8192 维只服务 grouping 召回；WeKnora 跨库检索要求所有库共享同一 `embedding_model_id`，换模型 = 全量重嵌入 | AIHOT 的向量永不出召回窗口，WeKnora 的向量永不回答门户列表（§6.1） |
| V6 | **`analyses.origin` 原生支持 `'rule'`** | `0001_core.sql:177` | 归族、自动放行等确定性判断有原生落点，不需要新表 |
| V7 | **公开读投影一行都不能改** | `publication/publish.ts:246-279` 是手工维护的 29 元组 `INSERT ... IS DISTINCT FROM`；漏一个元素 ⇒ `revision` 单调膨胀 ⇒ 下游抖动 | 任何扩展都以注入点方式接入，**不加列** |

**两个不对称需知晓**：WeKnora 有真 RBAC（`WK/internal/router/rbac.go`，635 行）与能力域 API Key，AIHOT 只有单一 admin 角色（`0004_admin_ops.sql:8` 的 `CHECK (role IN ('admin'))`）——阶段一先做企业登录 + 基础角色，细粒度权限后续迭代。WeKnora 的重复上传返回 `duplicate_*` 错误码而非 upsert（`WK/internal/handler/knowledge.go:165-177`）——入库契约必须按这个分支写（§6.1）。

## 1 职责切分

### 1.1 四个子系统的心智模型

| 系统 | 一句话职责 | 持有什么 | 绝不做什么 |
|---|---|---|---|
| **AIHOT 派生**（下文简称"平台"） | 车载行业动态的**管线 + 真相源 + 门户** | 信源注册表、报道与版本、事件聚类、判断记录、报告、门户、运维可观测 | 不做对话、不做长期知识索引、不做 PDF 解析、不做查询期 RAG |
| **WeKnora** | 知识与**问答**引擎 | 切分、向量、BM25、重排、GraphRAG、Wiki、FAQ、Agent 与技能沙箱 | 不持业务主数据、不持调度、不持爬虫、不做审批 |
| **RegPilot（hermes）** | **对话式业务代理**与投递前端 | 身份与铁律、评审交互、解读写作、飞书会话与卡片投递、面向人的提醒升级 | 不直写平台数据库、不做数据主存 |
| **飞书（表 + wiki）** | 迁移期的**汇报视图**与缓冲层 | 只读投影表、周报归档文档 | 最终不再是数据源 |

### 1.2 归属明细表

| 关注点 | 唯一写者 | 只读消费方 | 为什么在这 |
|---|---|---|---|
| 信源注册与调度健康 | 平台 `sources`/`fetch_runs` | 门户管理、RegPilot | `scheduleDueSources` + 自适应调频已存在 |
| 报道身份 / 版本 / 时间线 | 平台 `articles` | 一切 | 全仓最难替换的机制 |
| 三层相关性的**规则文本与排除词汇** | 平台 `industry/` 包 | — | 配置即代码、可评审、与提示词同版本 |
| 入选阈值 | 平台 `industry/selection.ts` | 评测台 | `tierThreshold()` 已读它 |
| 法规元数据追踪 | 平台 `industry/regulation/` 模块（§4） | 门户法规页、RegPilot | 在既有事件层之上做模块增强 |
| 切分 / 向量 / 索引 / Agent 行为 | WeKnora | 门户问答、RegPilot | 已在生产 |
| 原文**字节与目录** | 平台（§5） | WeKnora（拉取）、门户 | 字节在一侧，索引在另一侧 |
| 小报**内容** | 平台 `reports` + compose | RegPilot 渲染器、门户 | `composeDaily/Weekly/Monthly` 已存在 |
| 小报**卡片字节** | RegPilot（Python 渲染器） | 飞书群 | 单一渲染器铁律 BR-28 |
| 飞书群/单聊投递 | RegPilot（`deliver: feishu:…`） | — | 平台不参与投递 |
| 驱动对话与投递的定时 | RegPilot | — | 至少一次投递 + 补跑 |
| 驱动采集/解析/评分/报告的定时 | 平台 `schedules.ts` | — | `job_runs` + 告警 + 单例策略已具备 |

### 1.3 写路径铁律

1. **Python 永不直插平台数据库。** RegPilot/regwatch 触及平台数据只能通过 HTTP API。
2. **投影单向**：Postgres→飞书表、Postgres→WeKnora、Postgres→卡片。**投影永不成为数据源。**
3. **模型输出全部落 `analyses`**（append-only，`origin ∈ model|replay|rule`，带 `prompt_version` 与 `receipt_ids`）；**人工决定全部落带 `version` + `updated_by` 的 overrides 形表**。
4. **迁移期旧实现为基准。** 任何新旧不一致，默认判新实现有错。

## 3 核心策略：industry/ 包作为定制缝

### 3.1 AIHOT 的行业分离设计

AIHOT 已经把行业特定代码分离到 `industry/` 目录。这是本次重构的主要着力面——**替换 `industry/` 包的内容，就能把 AIHOT 从通用信息平台变成车载行业平台**，且不影响核心管线的合并能力。

```
industry/
  site.ts           ← 站点身份与品牌
  taxonomy.ts       ← 分类体系与标签枚举
  sources.json      ← 全部信源注册
  topics.json       ← 话题与关键词
  selection.ts      ← 入选阈值与法规权重
  features.ts       ← 功能开关
  prompts/*.md      ← 全部提示词（结构化解析、三层判定、摘要、报告撰写等）
  gold.example.jsonl
  brand/            ← 门户品牌配置
  pages/            ← 条款页等
  regulation/       ← ★ 法规模块配置（阶段二新增）
    lifecycle.ts    ← 六状态状态机定义
    relevance.ts    ← 三层合取判定 + 排除词汇
    identity.ts     ← code_norm / 族前缀 / 子项标记
    evidence.ts     ← 层级 → 印证状态
    weknora.ts      ← 库 ID + 嵌入模型 pin
```

### 3.2 信源注册（industry/sources.json）

所有信源在此声明式注册，平台首次启动时作为种子导入 `sources` 表，此后注册表归数据库 + 管理端管理。每源配置包括：

- `kind`：`rss` / `web_list` / `json_list`（零新增 kind，§7.2）
- `tier`：`T1` / `T1_5` / `T2` / `T3`（信源分级）
- `url` / `method` / `headers` / `bodyJson`：采集配置
- `itemsPath` / `urlTemplate` / `publishedAtUnit`：解析配置
- `denyUrlPrefixes` / `allowCategories` / `denyCategories`：围栏
- `participation_mode`：`hot_signal`（只贡献热度）/ 正常
- `initialBackfillLimit` / `initialBackfillMonths`：首次回填控制

### 3.3 分类体系与标签筛选（industry/taxonomy.ts + topics.json）

AIHOT 已有 `taxonomy.ts` + `topics.json` 实现分类与标签。门户首页的标签筛选（FR-02-02，"只看法律法规"/"只看 NCAP"/"只看新车发布"）直接复用此机制：

- **分类枚举**：法规动态 / 新车发布 / 技术落地 / NCAP 评测 / 客户动态 / 行业标准 / …
- **算法标签**：DMS / OMS / 座舱感知 / ADAS 视觉感知 / 车载数据安全 / …
- **法规类别**：国家标准 / UN 法规 / EU 法规 / NCAP 规程 / …

门户渲染时按 `articles` 关联的分类/标签做筛选，**不需要新表或新管线**。

### 3.4 提示词体系（industry/prompts/*.md）

所有模型提示词以 Markdown 文件存放在 `industry/prompts/`，运行时磁盘读取 + 内容哈希版本号。改提示词只影响**新**素材的判定，已判过的不重算——这是"改了规则但历史不改口"的护栏。

关键提示词：
- 结构化解析（含三层相关性判定指令）
- 法规编号/基干/阶段提取
- 摘要撰写
- 日报/周报/月报撰写
- 法规解读模板（阶段四）

### 3.5 入选阈值与法规权重（industry/selection.ts）

`tierThreshold()` 控制入选门槛。法规动态在热点排序中获得更高权重（FR-02-02、FR-09-02），通过 `selection.ts` 的权重配置实现——法规相关报道的 `hot_signal` 乘以法规权重系数，使其在热点排序中优先于一般行业动态。

## 4 法规模块设计（阶段二）

### 4.1 设计原则：模块增强，不动核心

法规追踪是在 AIHOT 既有事件层（`articles` → `facts` → `stories` → `publications`）之上的**模块增强**。核心策略：

1. **不新建独立实体表**（如 `regulations`、`regulation_families` 等）。法规元数据作为 `articles`/`stories` 的结构化扩展存储，通过 `analyses.output` jsonb 或模块级追加表承载。
2. **确定性匹配器独占法规编号解析**，以 `origin='rule'` 记判断（V6）。模型只做建议角色。
3. **状态机守卫在写路径上执行**，不用数据库触发器（避免存量脏数据阻塞迁移）。

### 4.2 法规元数据追踪

从 structure 阶段的解析结果中提取法规元数据，存入模块级表（仅追加，不改既有表）：

**`regulation_tracking`**（模块追加表）：

```sql
CREATE TABLE regulation_tracking (
  id              bigserial PRIMARY KEY,
  code_norm       text NOT NULL UNIQUE,       -- 规范化法规编号
  family_key      text NOT NULL,              -- 编号基干（归族键）
  title           text NOT NULL,
  lifecycle_state text NOT NULL DEFAULT '起草中'
    CHECK (lifecycle_state IN ('起草中','征求意见稿','报批稿','正式发布','已修订','已废止')),
  published_on    date,
  effective_on    date,
  comment_deadline date,
  revised_on      date,
  cert_type       text NOT NULL DEFAULT '待评审',
  corroboration   text NOT NULL DEFAULT '待核实',
  subscription_state text NOT NULL DEFAULT '待评审'
    CHECK (subscription_state IN ('待评审','高频监控','稳定低频')),
  origin_url      text,                       -- 官方原文链接
  origin_locked   boolean NOT NULL DEFAULT false,  -- BR-13
  source_tier     text,                       -- 首次报道的信源层级
  first_seen_at   timestamptz NOT NULL DEFAULT now(),
  last_check_on   date NOT NULL DEFAULT current_date,
  row_hash        text,                       -- BR-14
  updated_at      timestamptz NOT NULL DEFAULT now(),
  created_at      timestamptz NOT NULL DEFAULT now()
);
```

**`regulation_article_links`**（桥接事件层与法规追踪）：

```sql
CREATE TABLE regulation_article_links (
  regulation_id  bigint NOT NULL REFERENCES regulation_tracking(id),
  article_id     text   NOT NULL REFERENCES articles(id),
  relation       text NOT NULL DEFAULT 'subject',
  created_at     timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (regulation_id, article_id)
);
```

**`regulation_status_history`**（不可篡改的迁移史）：

```sql
CREATE TABLE regulation_status_history (
  id              bigserial PRIMARY KEY,
  regulation_id   bigint NOT NULL REFERENCES regulation_tracking(id),
  from_state      text,
  to_state        text NOT NULL,
  reason          text,
  actor           text NOT NULL,        -- 'pipeline' | 'admin:<id>' | 'feishu:<union_id>'
  origin          text NOT NULL CHECK (origin IN ('model','rule','manual','import')),
  article_id      text REFERENCES articles(id),
  at              timestamptz NOT NULL DEFAULT now()
);
```

### 4.3 生命周期状态机

`industry/regulation/lifecycle.ts` 定义状态机：

```ts
export const LIFECYCLE = {
  field: "lifecycle_state",
  order: ["起草中","征求意见稿","报批稿","正式发布","已修订","已废止"] as const,
  allowRegression: false,
  conditionalRequired: [
    { when: { lifecycle_state: "正式发布" },   require: ["published_on"] },
    { when: { lifecycle_state: "征求意见稿" }, require: ["comment_deadline"] },
    { when: { lifecycle_state: "已修订" },     require: ["revised_on"] },
  ],
  upsertPreserve: { subscription_state: ["高频监控","稳定低频"] },  // BR-18
} as const;
```

守卫在 `regulation/sync.ts` 的写入路径上执行：写入前校验状态转移合法性 + 条件必填 + 精度守卫（BR-12）+ `origin_locked` 守卫（BR-13）+ `upsert_preserve`（BR-18）。同事务写 `regulation_status_history`。

### 4.4 法规归族

归族判据是**符号结构**，不是向量相似度（向量空间里 `GB 44495.1-2024` 与 `GB 44495.2-2024` 和 `Euro NCAP 2026` 与 `Euro NCAP 2027` 长得一样，但前者应同族、后者不应）。

确定性匹配器规则（`industry/regulation/identity.ts`）：
- **BR-07 编号基干延续**：去掉版本标识（年份/Supplement/Rev）后基干相同 → 同族
- **BR-08 官方替代语义**：官方明确"代替 XX" → 同族
- **BR-09 NCAP 代际特例**：Euro NCAP 2023 与 2026 是并列规程代际 → 不同族（`family_kind='ncap_scheme'`）
- **BR-10 子项不单独追踪**：三态判定（确认子项/不确定/非子项），词边界保护 + 最长前缀优先

匹配器以 `origin='rule'` 写入判断记录（V6）。人工可经 overrides 否决，overrides 在任何自动召回之前短路。

### 4.5 排除清单

排除清单作为模块级表（`exclusion_list`），支持四种范围：

```sql
CREATE TABLE exclusion_list (
  id         bigserial PRIMARY KEY,
  scope      text NOT NULL CHECK (scope IN ('topic','regulation','pattern','source')),
  code_norm  text,           -- scope='regulation'
  topic_key  text,           -- scope='topic'：BR-01 排除清单
  pattern    text,           -- scope='pattern'：URL/标题模式
  source_id  text,           -- scope='source'
  reason     text NOT NULL,
  decided_by text,
  decided_on date,
  revoked_at timestamptz,    -- 撤销不删除
  created_at timestamptz NOT NULL DEFAULT now()
);
```

排除清单读取失败时整个流程中止（BR-17）。被排除的法规再次被采集到时立即拦下（BR-08-06）。

### 4.6 评审队列

阶段二在门户新增评审队列页面（FR-08-xx），展示待评审法规列表，支持：
- 停留天数读取时推导（`first_seen_at` → now()，>7 天醒目标记，>14 天升级提醒）
- 深读详情（是什么/涉及功能/为什么/核心要求/与我们的关系/行动项/来源）
- 三态决策（收录/降级/暂不关注）；RegPilot 通过 CT-3 调用平台 API 完成对话评审

**措辞边界（2026-10-09 Item 19）**：FR-02-06 的七个禁词（落表、防污染、订阅状态、印证状态、信源级别、待评审、运行统计）只约束**读者可见面**（公开出口 + 门户读者页面）。评审队列属**内部视图**，页面可以正常印「待评审」。落点：`apps/web/app/routes/regulation-review*.tsx`（阶段二 2.7）不受该禁令限制；`industry/prompts/report-daily-lead.md` / `report-period.md` 的深度不再扩。
- 三态决策：收录（→高频监控）/ 降级（→稳定低频）/ 暂不关注（→写排除清单）
- 每个决策记录决策人、日期、原因

评审交互允许在对话渠道完成（RegPilot 调用平台 API），门户有等价队列。

## 5 原文库模块设计（阶段三）

### 5.1 归属：字节在一侧，索引在另一侧

**原文 PDF 的字节与目录归平台；WeKnora 只持派生物。**

理由：法律语料需要工件的记录（版本、层级、来源、受限标记、替代关系），WeKnora 建模的是知识项，没有这些概念。且 WeKnora 的去重是拒绝重复（`duplicate_*`），而我们需要重复归因（同一份 PDF 覆盖多条子项法规）。

### 5.2 平台侧：文档目录与字节

```sql
CREATE TABLE documents (
  id             bigserial PRIMARY KEY,
  sha256         text NOT NULL UNIQUE,           -- 内容寻址
  regulation_id  bigint REFERENCES regulation_tracking(id),
  title          text NOT NULL,
  origin_url     text NOT NULL,
  source_tier    text NOT NULL CHECK (source_tier IN ('T1','T1_5','T2','T3')),
  restricted     boolean NOT NULL DEFAULT false,  -- 受限原文不得进对外出口
  parse_state    text NOT NULL DEFAULT 'pending'
    CHECK (parse_state IN ('pending','parsed','pushed','indexed','failed')),
  parsed_md      text,                            -- 解析后的 Markdown
  parser_id      text NOT NULL DEFAULT 'mineru',  -- 解耦解析器标识
  weknora_kb_id  text,
  weknora_knowledge_id text,
  created_at     timestamptz NOT NULL DEFAULT now(),
  updated_at     timestamptz NOT NULL DEFAULT now()
);
```

原文字节存储在文件系统/对象存储，`documents` 表持有目录与元数据。

**关键陷阱**：平台的过期清理 `operations/retention.ts:34` 按 `expires_at` 删 `stored_files`——原文一旦入库，必须排除 `purpose='regulation_original'`，且 `origin_ingested='已入库'` 的原文永不自动过期。

### 5.3 解耦解析器（MinerU Cloud 为默认）

解析器通过配置注入，接口统一：

```ts
// industry/regulation/parser-config.ts
export interface DocumentParser {
  id: string;
  name: string;
  parse(input: { filePath: string; mimeType: string }): Promise<{ markdown: string; pages?: number }>;
}

// 默认实现：MinerU Cloud
// 未来可替换为其他解析器，类似 WeKnora 的 docreader 配置方式
// 解析目标类型：主要 PDF（法规原文）+ 少量 HTML 页面
```

解析器配置（端点、密钥、超时等）存放在环境变量或配置文件中，不进代码仓库。

### 5.4 门户检索与显示

- 门户新增原文库页面（FR-04-05）：按编号、标题、分区、业务分类检索
- 检索结果以解析后的 Markdown 作为源显示（FR-04-06）
- 法规详情页显示站内原文解析链接 + 官方原文链接（FR-03-07）
- 受限原文（`restricted=true`）不得进对外可读出口（FR-04-07）

## 6 跨边界契约详节

### 6.1 CT-1 平台 → WeKnora（原文入库与重解析）

| 项 | 规定 |
|---|---|
| 触发 | `documents.parse_state='pushed'`（解析完成且已推送意图持久化） |
| 端点 | `POST /api/v1/knowledge-bases/:id/file`；API Key 按库作用域 |
| 幂等 | 字节 sha256 + 目标库。`duplicate_*` **算成功**：查到已有对象 ID 并回写 |
| 状态机 | `pending → parsed → pushed → indexed`（失败 `failed`）。先持久化意图再调用 |
| 重解析 | 仅在 sha256 变化或运营者明确指令时；仅元数据变化用 `reuse_vectors` |
| 前置断言 | 上传前断言 `kb.embedding_model_id === PINNED`（V5） |
| 对账 | 夜间双向孤儿报告：平台有但 WeKnora 没有 → 重推；WeKnora 有但平台没有 → 报告（不自动删除） |

### 6.2 CT-2 WeKnora → 使用者（问答与引用回链）

入库时经 `PUT /api/v1/knowledge/tags` 打标签：`portal:<门户永久链接>`、`regcode:<code_norm>`、`tier:<T1|T2|T3>`、`sha:<sha256>`。

回答的每条引用必须携带：对象 ID + 分块 ID + `regcode` + `portal` URL。渲染层据此产出 `[原文](门户链接)` 与来源链接，**禁止只给知识层内部 ID**（FR-07-02）。

### 6.3 CT-3 RegPilot → 平台（对话完成业务动作）

RegPilot 以服务主体身份调用平台的管理 API（不为它单开一套 API，守卫/审计/权限检查全在 `adminHandler` 里）：

| 端点 | 用途 |
|---|---|
| `GET /api/admin/regulations?review=pending` | 取评审队列 |
| `POST /api/admin/regulations/:code/review` | 评审决策 |
| `POST /api/documents` | 推送器上传原文 |

### 6.4 CT-4 平台 → 飞书表（单向投影，迁移期）

- 单向，15 分钟节奏
- 遵守 `upsert_preserve`；平台算不出来的格子绝不投空值去覆盖
- 幂等：逐行 `row_hash` 比对，零差异不调 API
- **没有冲突解决，因为没有任何东西读飞书表**

### 6.5 CT-5 平台 ↔ RegPilot（小报：出内容不出卡片）

接口是一份**内容 feed**：`GET /api/v1/reports/weekly?key=<周期标签>` 返回有序条目 + 分区 + 导语。RegPilot 的 Python 渲染器消费它、产出卡片字节。

迁移期：平台的内容推送目标保持 disabled，群卡片与单聊由 RegPilot 投。

### 6.6 内网出访（V3 的具体处置）

设一个窄口径 `INTERNAL_EGRESS_ALLOW`（host:port 列表），WeKnora 客户端走 `route:"direct"`。**不开 `ALLOW_PRIVATE_NETWORK_FETCH`**。

## 7 采集适配器裁决

### 7.1 决策规则

做成平台声明式配置，当且仅当全部满足：① 列表可声明式获得；② 日期与 URL 抽取可用选择器 + 正则 + 单位表达；③ 朴素 fetch 带 UA 能通过；④ 节奏是每源调频；⑤ 希望正文抽取/初筛/评分在同一队列里跑。

否则**做成外部推送器**（`POST /api/ingest/items`）：需要真实浏览器、付费第三方、登录/反爬循环、或必须与 worker 隔离的失败域。

**7 GB 机器上的推论**：worker 容器里放浏览器是最大的内存风险（一个 Chromium 约 300–500 MB）。**浏览器永不进平台容器。**

### 7.2 逐站裁决

| 站点 | 裁决 | 机制 |
|---|---|---|
| SAC / 国标委 | **`json_list`** | `mode:'html_window_var'`、`publishedAtUnit:'yyyymmdd'` |
| C-NCAP | **`json_list` × 5 源** | `method:'POST'`+`bodyJson`+`headers`+`jsonKey` |
| MIIT 政策文件 | **`rss` × 2** | RSSHub 镜像 + 原生 RSS |
| UNECE / WP.29 | **`rss`** + `web_list` | |
| Euro NCAP Newsroom | **`rss`** | |
| EUR-Lex | **外部推送器** | TLS 指纹/WAF，推送器自带代理 |
| IVISTA / CATARC | **外部推送器** | 列表需真实浏览器 |
| 中汽中心 / 标准化站点 | **`web_list`** | 选择器列表 + `detail` 取日期 |

**净结论：采集侧零新增 kind。** 这是 V1 的直接后果。

### 7.3 若真要加 kind：四位一体

四处全部必改：① 迁移里 `DROP`+`ADD` `sources_kind_check`；② `sources/types.ts` 的 kind 联合 + `publication/rules.ts` 的 `channelOf()`；③ `sources/config-keys.ts` 的 `KEYS`（没有 default 分支，未注册的 kind 静默拒绝所有配置项）；④ 抓取模块 + `collect.ts` 分派。

## 8 与上游 AIHOT 的兼容策略

### 8.1 核心原则

- **对 AIHOT 核心代码的改动最小化**，优先通过 `industry/` 包注入领域配置
- **必须修改的**：`industry/` 包全部内容（信源、分类、提示词、筛选规则）

- **删除的**：AIHOT 自带的模型榜单与订阅额度监控两个模块（在派生时关闭或删除）

- 新增的后端业务代码集中到 `packages/backend/src/regulation/` 与 `media/documents.ts`，**不散改进上游文件**

### 8.3 上游更新合并流程

1. 上游发布新 commit → 在派生分支 rebase

## 9 运维设计

### 9.1 拓扑与内存

知识层保持在其现有主机（172.17.12.199），**不合并**。应用机上的预算：

| 容器 | 预算 | 关键旋钮 |
|---|---|---|
| Postgres 17 | 900 MB–1.2 GB | `shared_buffers=256MB`、`work_mem=8MB` |
| API | 250 MB | `--max-old-space-size=256` |
| Worker | 500 MB | 分析并发 2、正文抽取局部并发 1 |
| 门户 SSR | 350 MB | `--max-old-space-size=320` |
| RegPilot + 网关 | 700 MB | 一个进程 |
| Caddy | 50 MB | |

稳态约 3.0–3.5 GB。关闭 AIHOT 自带的榜单与额度监控模块。

### 9.2 消除"两套 Python"

1. **平台容器里零 Python。** 镜像只有 Node 24
2. **恰好两个解释器**（RegPilot 框架 + 业务虚拟环境），各以绝对路径固定
3. **跨界只走 HTTP/JSON**：无 import、无共享 venv、无 subprocess
4. **`doctor` 在部署期失败**：TS 侧查迁移状态、源配置、预算、知识层可达性；Python 侧跑 import 探针

### 9.3 迁移与启动安全

- 保留一次性 `setup` 容器（迁移 + 种子）；不从 worker 跑迁移
- 迁移里不能有 `CREATE INDEX CONCURRENTLY`（事务内不允许）
- 种子是非破坏性的（只插不存在的、永不回滚后台编辑）
- 法规写入器读 `REG_IMPORT_MODE=dryrun|write`，首次启动断言为 `dryrun`

### 9.4 成本、预算与限速

1. 模型网关注册为单一服务名（`caret`），`per_minute=36`（低于 40，给 RegPilot 留头）
2. 需要在全局模型客户端加一个容量 5 的信号量（预算表达不了并发）
3. 单条资讯 ≈ 5 次付费调用 + 分块 + 可选聚类 1–2 次 + 翻译。100 条/日 ≈ 800 次调用
4. 分块是独立服务名与独立预算行
5. RegPilot 与平台各用各的密钥与服务端配额

### 9.5 告警分域

- **平台拥有数据面**：信源失败、预算熔断、报道卡住、发布链断裂、评审队列深度
- **RegPilot 拥有对话面**：任务派发失败、投递错误、技能报错
- **绝不双播**
- 扩展"无写入静默检测"：N 天没有新法规写入就告警

## 10 关键取舍

### 10.1 被否决：把法规建模为独立实体层（重方案）

原方案新建 `regulation_families` / `regulations` / `regulation_lineage` 等 8 张表，完整的 DDL + 状态机守卫 + 评审闸门 + RBAC。

否决理由：
- 与"减少代码大修改、最大化复用 AIHOT"的核心原则冲突
- 在 73 条法规的规模上，独立实体层的维护成本高于收益
- 法规追踪可以作为事件层的**模块增强**实现，不需要平行的实体系统
- 阶段四的解读/对比/问答模块更需要稳定的法规标识，但不需要重型 schema

### 10.2 被否决：给 `publications` 加列

代价（V7：29 元组四处同步 + 全量重发扫描 + 静默抖动风险）远高于收益。任何扩展以注入点方式接入。

### 10.3 被否决：数据库触发器

存量脏数据会让整次导入失败。改为写路径守卫 + 巡检报告。

### 10.4 被否决：门户自带爬虫

V1 已证声明式采集覆盖大部分信源，需浏览器的缩到 EUR-Lex + IVISTA/CATARC，两者做外部推送器。
