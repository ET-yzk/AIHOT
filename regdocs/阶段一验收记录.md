`npm test` 的失败测试名固定是这 8 个，与本地修改无关，原因写在 FORK-CHANGES 的「本地测试基线」：

**判断有没有引入回归要比对失败测试的名字，不是看红绿数量。** 这 8 个必须在 Linux 的 CI（`.github/workflows/check.yml`）上跑绿才算过。
**2026-10-08 顺着当天那个坑，把 `.github/workflows/check.yml` 逐行按「这一步的退出码会不会被吃掉」读了一遍，能本机量的都量了。** 先量最根本的一条：GitHub 的 `run` 步骤**不写 `shell:` 时用的是 `bash -e {0}`，只有显式 `shell: bash` 才带 `-o pipefail`**（[workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax)），而这份文件**一处 `shell:` 都没写**，所以 CI 里也没有 pipefail——本机对照复现：`bash -e -c 'false | true'` 交回 **0**，`bash -eo pipefail -c 'false | true'` 交回 **1**。逐条走下来**结论是今天没有假绿**：真正当门禁的几步都是单条命令（`:48` `npm run typecheck`、`:50` `npm run build -w @aihot/web`、`:52` `node --test apps/web/tests/*.test.ts`、`:67` 与 `:103` 的冒烟、`:70` `npm test`、`:98` `docker compose up -d --build`），断言型的管道都以**判据命令**收尾——`:106` 的 `psql … | grep -qx "$EXPECTED"` 就算 psql 死了、输出为空，`grep -qx` 自己返回 1；`:105` 的 `EXPECTED=$(node -e …)` 在 `-e` 下会让整步一起红；`:93-94` 那两条 `grep -qx` 正是为「sed 静默失配」设的守卫；`:73` 的 `|| true` 是故意的，且整步 `if: failure()`。**但有两处「看着像断言、其实不是」**：`:66` 与 `:101` 那两个等健康的循环（`curl … && break; sleep N;`）——本机量下来**循环耗尽之后整步是 0**（最后执行的是 `sleep`，`curl` 的失败被 `&&` 豁免），今天不出事只因为它们的下一行就是冒烟门禁。**留给以后动这个文件的人两句**：① 不要把门禁写成 `… | tail`／`… | head`，这里没有 pipefail 兜底——当天我正是在交互式 shell 里被 `grep … | tail -2` 掩掉了一条早已断掉的 `&&` 链（就是本节上面那四条纠正里的 (1)）；② 等健康的循环若本意是断言，末尾补 `|| exit 1`，或让后面的门禁自己带上「服务已就绪」的证据。**这一道今天也按新规矩重测了**：`dev` = `3dfa614`，`npm run typecheck` 作为单独一条命令交出 **exit 0**（日志 `.data/typecheck-3dfa614.log`）。**收工前把这条审计走完了**，两点补充：`.github/workflows/` 里**只有 `check.yml` 一个文件**，且**全文一处 `shell:` 都没有**（`grep -rn "shell:" .github/workflows/` 零命中）——所以「不声明 shell 就走 `bash -e`、没有 pipefail」对**每一步**都成立，不是某一行的特例；两个门禁脚本自己也查了，`npm test` 是光一条 `node --test --test-concurrency=1 --test-timeout=120000 "tests/*.test.ts"`（glob 由 node 自己展开，不经管道），`npm run typecheck` 是七段 `&&` 链，在 `-e` 下第一段失败就整步红——**所以「typecheck exit 0」证明七段都跑过，而它红了只告诉你第一段红在哪**。最终结论：**这套门禁面上没有任何一处会因为退出码被吃掉而假绿**，唯一两处「看着像断言其实不是」的就是上面那两个健康循环，而它们后面紧跟的冒烟步骤替它们兜着。**重的那道门禁也在这串只改 `.md` 的头之后复跑了一次**：`dev` = `bcaed5f`，全新库 `aihot_dev182d_test`（37 个迁移 + `seed --topics-only` 的 30 个主题），只设 `DATABASE_URL`、`MODEL_CALLS_ENABLED` 保持未设，墙上 **13 分 27 秒**（`duration_ms 806960`）——**182 / 174 通过 / 2 失败 + 6 取消**，红的八个名字与基线逐字相同（五条 SIGTERM、一条 batch、三条 translate；日志 `.data/suite182d.log`）。这次连跑顺带旁证了本节上面那条判据：`eb4793d → bcaed5f` 之间**只有 `.md` 改动**，而套件交回同样的数——**但这是旁证不是凭据**，凭据仍是那条返回 0 命中的「有没有代码打开过这两处文档」的命令。

本次验收过程中新发现并修掉的两个「看起来像回归、其实是本地可运行性」问题：

1. `apps/web/server.ts` 用 `await import(<Windows 绝对路径>)` 载入 SSR 产物，ESM loader 把盘符当成协议（`Received protocol 'c:'`）拒绝，生产 web 服务在这台机器上一启动就崩，连带 `apps/web/tests/cache.test.ts` 的 9 个用例全红。改成 `pathToFileURL(...).href`。

3. 同一个文件还踩了第二道闸门：`selected_ledger.visible_at`。台账里只要有一条还在未来的行，可见前沿就停在那儿，排在它后面的条目（包括本文件自己刚发布的那条）一律读不到，投影于是报「什么都没要发」。现在每轮清掉指向已删文章的台账行，并把还在未来的放行。

**库里跨轮残留会造出假红。** 同一个复用库连跑两次全量套件，第二次多红了 `tests/events.test.ts` 的「two stories stay apart…」；单独在全新库（`CREATE DATABASE` + `migrate` + `seed --topics-only`）跑那个文件是 10/10，全量套件在全新库（`aihot_stage1_test`）重跑也只剩那 8 个。认基线之前先确认库是新建的——CI 每次用的就是现迁的库；否则该排查的是残留，不是改代码。

4. **新出现的假红候选，记下来免得每次重新查：** 改名那条分支第一次全量跑（`aihot_portal_test`）多红了 `tests/feishu-projection.test.ts` 的「the mirror carries the portal's rows, and an unchanged row is never sent twice」，断言信息是 `portal said 1: ["新规 1-…"]`（要 2 条，门户只读到 1 条）。同一个 commit 换一棵新库再跑一次就只剩那 8 个；把这三个文件（`publication`、`reports-feed`、`feishu-projection`）单独连着跑也是全绿。**2026-10-01 又专门按「残留」这个假设试过一轮最强的复现条件**：拿一棵刚跑完整套全量、装着别的文件留下的 selected/publication 行的库（`aihot_packrules_test`），把这个文件单独连着跑 **6 次，30/30 全绿**。它本来就有的两道防线也对得上「不是残留」：`reset()` 清掉本文件的行并把任何未来的 `selected_ledger.visible_at` 提前到当下，`settle()` 先把别人留下的行投影掉再归零计数器。所以这个名字的红先按「负载」看，重跑确认之后才当回归查。

5. **整套件同时红一片、且日志不再长：先看 Docker，不要看代码。** 2026-09-30 05:22 那次（`aihot_decon2_test`）跑到一半 `aihot-pg` 容器被外力停掉（`docker ps -a` 是 `Exited (255)`，容器自己的日志停在一条 checkpoint 上、没有任何 shutdown 记录），于是 40 个测试名一起变红，横跨 analyze、media、events、publication、feishu 等互不相干的文件，`node --test` 也卡在那里没有小结。**认法：红的名字跨文件一大片 + 日志字节数连续几分钟不再增长 = 库没了**，与那 8 个「每次固定」的名字是两回事。`docker start aihot-pg` 之后换一棵新库重跑即可。
   顺手把一件安全上的事查实了：这类测试库是 `seed.ts --topics-only` 迁出来的，**里面没有包里的信源**（那次的 `sources` 表只有 1 行，是 `test-analyze-stop-…` 那条本地桩）。所以就算有孤儿 worker 进程带着默认开启的 `COLLECT_ENABLED` 活着，它也没有真信源可抓，不会去碰国标委/工信部/Euro NCAP/C-NCAP。测试库里的信源永远是 `example.org` 和本地桩，这一条比「记得关安全阀」更硬。

6. **单独跑测试文件要带上 `npm test` 的那两个参数。** 根 `package.json` 的 test 脚本是 `node --test --test-concurrency=1 --test-timeout=120000 "tests/*.test.ts"`；裸跑 `node --test tests/translate-shutdown.test.ts` 没有默认超时，Windows 上那个子进程又收不到 SIGTERM，于是**整轮永远挂着不出小结**（这次白等了 40 多分钟）。凡是会 spawn 子进程的测试文件，单独跑一定要加 `--test-timeout=120000`。

7. **自己起服务看站点之前，先确认端口上坐的是你刚起的那个进程。** Windows 上 `node apps/api/src/main.ts` 撞端口会打一行 `EADDRINUSE` 就**退出**，而 `curl` 照样回 200——因为端口上还有上一轮遗留的 api 在答话，读的是**另一棵库**。2026-09-30 就这么被骗了一次：页面上出现代码里早已改掉的示例行业桩文本，看着像「改名没改干净」，其实看的是旧数据。两条便宜的认法：起完 `grep EADDRINUSE` 那份日志；或者把 API 返的某条 id 拿去 `select count(*) from articles where id='…'` 在你指定的库里查（另一棵库里应当是 0）。遗留进程用 `netstat -ano | grep 127.0.0.1:3001` 拿 PID，再用 `powershell Get-Process -Id <pid>` 看它的启动时间确认是谁的，别顺手杀用户自己的 dev 服务。

## 5 回滚实测

## 23 分叉清单原来只有两半，第三半是 101 个删除：230 条路径逐个对着上游现在的树分了一次类

`FORK-CHANGES.md` 的分叉清单写的是「分叉的**两半**各由一条命令定死：`$1=="A"` 与 `$1=="M"`」。今天照这句复量才发现**它漏了第三半**：完整的一句 `git -c core.quotePath=false diff --name-status -M main dev` 交出 **230 条 = 26 `A` + 103 `M` + 101 `D`**。那 101 个 `D` 就是 1.1 摘掉的两个模块和随它们去的东西——它们记在本文 1.1 那一节里，却从没进过「两半」这个口径。**清单少算一半不是文字问题：modify/delete 恰恰是 rebase 里唯一必须人来判的那一类**，而它正好只出现在第三半里。

**分类的跑法（只读，两条命令加一次 join）**：

```bash
git -c core.quotePath=false diff --name-status -M main dev           > /tmp/ours.txt
git -c core.quotePath=false diff --name-status -M main upstream/main > /tmp/theirs.txt
# ours 的每条路径，按 theirs 对同一个路径做了什么归类（两份名单都是 tab 分列；R 行是 old、new 两列）
```

| 我们做了什么 | 上游现在对它做什么 | 条数 | 合并时是什么 |
|---|---|---|---|
| `M` | 也 `M` | **86** | 两边都改，真正的工作量；第 10 节那个 80 文件的合并预览集中在这一堆 |
| `M` | 搬走了（`R`） | **9** | 我们的改动要重放到新路径上，名单在下面 |
| `M` | 删了 | **3** | modify/delete，判「保住我们这份」还是「接受删除」 |
| `M` | 没碰 | 5 | 原样带过去 |
| `A` | 也新建了同名文件 | **1** | add/add，两边内容不同 |
| `A` | 没有这个路径 | 25 | 原样带过去 |
| `D` | 也删了 | **100** | **同向收敛**，什么都不用做 |
| `D` | 搬走了 | 1 | 我们删的正是它改名的那个文件（`leaderboard/BrandMark.tsx`），第 10 节那两条 rename/delete 就是它 |

**三格加法都自己闭合**：`M` 86+9+5+3 = 103；`D` 100+1 = 101；`A` 25+1 = 26；合计 230，与第一句那条命令逐字一致。**两天后（2026-10-08）这条命令变成了 232 = 28 `A` + 103 `M` + 101 `D`**，多的两条正是这一节之后合入的 `tests/notify-deliver.test.ts` 与 `scripts/audit-divergence.ts`——**这就是为什么这套分类不该只活在文档里**：`node scripts/audit-divergence.ts` 每次重算，包括把改名阈值压到 10% 去逮那种「上游搬走了、两边又各自重写」的静默接管（它第一次跑就逮到第二条：`tests/url.test.ts → tests/url.standalone.test.ts`，相似度 34%，与 `industry/site.ts` 那一类同性质）。

**2026-10-08 又 fetch 了一次上游，这一节的结论经住了一次时间考验。** 上游从 `2b80294` 走到 `6e67a9d`（当天 13:55 的提交），**落后从 66 个 commit 变成 83 个**，上游那侧的路径从 634 条变成 **644** 条。可是把两边都重跑一遍，**冲突面一格没动**：`git merge-tree` 的合并预览还是 **80 个文件**，类型分布还是 content 74 / modify-delete 4 / rename-delete 1 / add-add 1；我们这侧的分类还是 232 条路径、86 个两边都改、9 个被搬走、3 个上游删了（其中 2 个是低阈值才配出来的重写式搬家，就是上面那两条）、100 个同向删除。**这条对第 13 条很要紧**：它说明上游这两天多出来的 17 个提交几乎全落在我们**没碰过**的文件上，rebase 的成本没有随着上游活跃而涨——**要抄的是这个稳定性，不是 66 或 83 那种数字**，那类数字只能由工具现场给。

**最该记住的一格是那个 100。** 我们 1.1 删掉的 101 个文件里，**上游今天自己删了 100 个**——这条派生看起来最「与上游作对」的一步（把榜单与配额整个摘掉），上游在这一年里自己走了一遍。所以 rebase 的那一步不是分叉而是收敛。代价分布也因此说清了：**我们动过的 129 个路径（26 `A` + 103 `M`）里，86 个是两边都改的大头，30 个（25 `A` + 5 `M`）上游根本没碰、原样带过去，剩下要你判的一共只有 5 个。**

## 24 投递状态机（sent / failed / unknown）今天仍然零覆盖，测试设计已备好但被权限层挡住

第 23 节那条工具链跑完之后，接着做的是把 `notify/deliver.ts` 文件头那三句承诺也钉住——**它们目前只靠散文**：`sent`/`failed`/`unknown` 怎么分、`resendDelivery` 只对 `unknown` 与 `failed` 开放、以及 `markStaleDeliveries` 那句「**Nothing is re-sent automatically**」。第 22 节那四条用例钉住的是「不回填」（写之前就被拦下），这六条钉的是**写下去之后**会发生什么，两者互补。

**设计（照着就能写，全部离线）**：假服务只听 `127.0.0.1`（`createServer` + `listen(0, "127.0.0.1")` 拿随机端口），把目标的 `config_ref` 指向 `FEISHU_PUSH_WEBHOOK_URL`，`credential()` 读的是 `process.env`，所以测试里赋值即生效；**翻开 `config.feishuContentPushEnabled` 之前先断言 URL 是回环**（`assert.ok(url.startsWith("http://127.0.0.1:"))`），最后一条用例结束时把阀恢复成 false——这样「开发/测试期安全阀关着」那条规矩没有被破坏，出站目的地也只有本机。

| 用例 | 喂给它的返回 | 断言的是 |
|---|---|---|
| 200 + `{"code":0,"msg":"ok"}` | 正常 | 状态 `sent`、`sent_at` 非空、假服务恰好收到 1 次 |
| 200 + `{"code":94,…}` | HTTP 成功但飞书报错码 | **明确拒收**记 `failed`（`deliver.ts:60` 那行的另一半），`response` 里带着那个 body |
| 500 | 服务端错误 | `unknown` 而不是 `failed`——「可能已经送达」不能冒充「没送达」 |
| 连不上（`http://127.0.0.1:1/hook`） | fetch 抛错 | 走 `catch` 分支记 `unknown`（`deliver.ts:65-68`） |
| 手工重发 | — | 对 `sent` 的行调 `resendDelivery` 必须抛 `delivery N is sent`；对 `failed` 的行重发才真的再发一次，`attempts` 变 2 |
| 进程中断留下的行 | 直接插 `sending`/`pending` 且 `updated_at` 早于 15 分钟 | `markStaleDeliveries` 把 `sending`→`unknown`、`pending`→`failed`，**新鲜的那条不动**，并且假服务的计数**一次都没增加**——这才是「不自动重发」的观测而不是一句承诺 |

**为什么写不进去**：使用者 2026-10-08 已经点头「允许我编辑这个已存在的测试文件」，但 `Auto` 模式下的分类器**看不到那次回答**（它回的是「在当前许可上下文未变更前不可重试此操作」）。按本仓库的老规矩——**权限层拒绝就停下问，不改形态重试**——我停在这里：没有换 `Write` 整文件覆盖、没有新建文件绕过去。要落地只需要把这句授权交到许可层手里，两种办法之一：把这一轮的模式换成 `acceptEdits`（或 `bypassPermissions`），或者让编辑真的弹出授权提示时点「允许」。之后照上面那张表写，单文件跑（`node --test --test-concurrency=1 --test-timeout=120000 tests/notify-deliver.test.ts`，全新库）+ 变异验敏感性（把假服务的 500 改成 200，只有那条 `unknown` 用例该红）+ `npm run typecheck`，在 `feature/notify-send-state-machine` 上提交后合回 `dev`。**分支已建好、代码没动过一行**，`dev` 仍是 `beb82e3`。

**顺手记一条负面结论，免得下一次有人想走捷径**：把改名阈值调低（`-M20%`、`-M10%`，或合并时 `-X find-renames=…`）**不能**解决这一条。阈值降到 10% 确实让 git 报出 `R014`，但那等于命令 git 把两个只有 14% 相同的文件当成同一个来合——**它会把两边的文案搅成一份**，比现在这个「安静地拿上游那份」更难发现。相似度低于一半的这一类，正确处置只有一种：人照着旧文件把新路径那份重写一遍。
