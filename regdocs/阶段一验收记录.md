## 3 后端套件的已知红

`npm test` 的失败测试名固定是这 8 个，与本地修改无关，原因写在 FORK-CHANGES 的「本地测试基线」：
5 个 `SIGTERM` 用例（Windows 上没有 POSIX 信号，子进程被直接终止，测试等到超时）+ 3 个 `tests/translate.test.ts` 用例（打桩 provider 的并发行为在这台机器上不稳定）。
**那三个 translate 的红不是机器缺信号**：2026-09-30 把它们单独在全新库（`aihot_decon_test`）跑，是 **3/3 全绿**——红只在整套件同一个库里连跑时出现，来自测试文件之间的相互影响（共用库、并发跑作业）。所以这三个名字出现时先按「连跑相互影响」看，别去查信号。
**判断有没有引入回归要比对失败测试的名字，不是看红绿数量。** 这 8 个必须在 Linux 的 CI（`.github/workflows/check.yml`）上跑绿才算过。

本次验收过程中新发现并修掉的两个「看起来像回归、其实是本地可运行性」问题：

1. `apps/web/server.ts` 用 `await import(<Windows 绝对路径>)` 载入 SSR 产物，ESM loader 把盘符当成协议（`Received protocol 'c:'`）拒绝，生产 web 服务在这台机器上一启动就崩，连带 `apps/web/tests/cache.test.ts` 的 9 个用例全红。改成 `pathToFileURL(...).href`。
2. `tests/feishu-projection.test.ts` 假设门户是空的，而测试文件共用一个库，`tests/publication*.test.ts`、`tests/reports-feed.test.ts` 留下的入选条目会一起进投影，于是「这次新建了几行」的绝对计数变成 22。现在每轮先 `settle()` 投影一次再清零发送记录，计数只代表本文件刚发布的东西。
3. 同一个文件还踩了第二道闸门：`selected_ledger.visible_at`。台账里只要有一条还在未来的行，可见前沿就停在那儿，排在它后面的条目（包括本文件自己刚发布的那条）一律读不到，投影于是报「什么都没要发」。现在每轮清掉指向已删文章的台账行，并把还在未来的放行。

**库里跨轮残留会造出假红。** 同一个复用库连跑两次全量套件，第二次多红了 `tests/events.test.ts` 的「two stories stay apart…」；单独在全新库（`CREATE DATABASE` + `migrate` + `seed --topics-only`）跑那个文件是 10/10，全量套件在全新库（`aihot_stage1_test`）重跑也只剩那 8 个。认基线之前先确认库是新建的——CI 每次用的就是现迁的库；否则该排查的是残留，不是改代码。

4. **新出现的假红候选，记下来免得每次重新查：** 改名那条分支第一次全量跑（`aihot_portal_test`）多红了 `tests/feishu-projection.test.ts` 的「the mirror carries the portal's rows, and an unchanged row is never sent twice」，断言信息是 `portal said 1: ["新规 1-…"]`（要 2 条，门户只读到 1 条）。同一个 commit 换一棵新库再跑一次就只剩那 8 个；把这三个文件（`publication`、`reports-feed`、`feishu-projection`）单独连着跑也是全绿。所以这个名字的红先按「负载/残留」看，重跑确认之后才当回归查。

5. **整套件同时红一片、且日志不再长：先看 Docker，不要看代码。** 2026-09-30 05:22 那次（`aihot_decon2_test`）跑到一半 `aihot-pg` 容器被外力停掉（`docker ps -a` 是 `Exited (255)`，容器自己的日志停在一条 checkpoint 上、没有任何 shutdown 记录），于是 40 个测试名一起变红，横跨 analyze、media、events、publication、feishu 等互不相干的文件，`node --test` 也卡在那里没有小结。**认法：红的名字跨文件一大片 + 日志字节数连续几分钟不再增长 = 库没了**，与那 8 个「每次固定」的名字是两回事。`docker start aihot-pg` 之后换一棵新库重跑即可。
   顺手把一件安全上的事查实了：这类测试库是 `seed.ts --topics-only` 迁出来的，**里面没有包里的信源**（那次的 `sources` 表只有 1 行，是 `test-analyze-stop-…` 那条本地桩）。所以就算有孤儿 worker 进程带着默认开启的 `COLLECT_ENABLED` 活着，它也没有真信源可抓，不会去碰国标委/工信部/Euro NCAP/C-NCAP。测试库里的信源永远是 `example.org` 和本地桩，这一条比「记得关安全阀」更硬。

6. **单独跑测试文件要带上 `npm test` 的那两个参数。** 根 `package.json` 的 test 脚本是 `node --test --test-concurrency=1 --test-timeout=120000 "tests/*.test.ts"`；裸跑 `node --test tests/translate-shutdown.test.ts` 没有默认超时，Windows 上那个子进程又收不到 SIGTERM，于是**整轮永远挂着不出小结**（这次白等了 40 多分钟）。凡是会 spawn 子进程的测试文件，单独跑一定要加 `--test-timeout=120000`。

## 5 回滚实测

实施方案写的阶段一回滚是「`industry/` 包恢复上游默认值 + 信源 `enabled=false`，核心管线未改动，回滚是纯配置操作」。实测了一次（在一条一次性分支上 `git checkout main -- industry` 再 `npm run typecheck`）：

- **回滚到本仓库自己的 `industry/` 包（dev 上那份车载包）确实是纯配置操作**，`git checkout dev -- industry/` 之后类型检查、构建、站点都正常，把 `sources.enabled` 置 false 即可停止采集。
- **回滚到上游示例包不是**：`packages/backend/src/publication/items.ts` 读 `PUBLIC_CATEGORY_FOLDS`（1.3 加进包契约的导出），上游示例包没有这个成员，`tsc -p packages/backend` 直接报 `has no exported member 'PUBLIC_CATEGORY_FOLDS'`；`tests/industry-pack.test.ts` 同理。要把包整个退回上游示例，得连 1.2/1.3 引入的包契约一起退，那不是纯配置。

结论：把回滚目标写清楚——**是 `dev` 上的车载包，不是上游示例包**。实测用的分支已删除，工作树没有留下改动。
