# 阶段一验收记录

留档要求来自实施方案的 G7：每一阶段的 DoD 必须含验收脚本输出留档 + 回滚方式实测一次。
本文只记阶段一（行业动态）在**这台 Windows 开发机**上实际跑出来的结果。跑法都写在这里，下次照抄即可复现。

开发分支模型：`main` = 上游 fork，`dev` = 主线，一个功能一条 `feature/*` 分支，测试无误才合回 `dev`。
本次全部在本地，**没有任何推送**。工作树用 `../.wt-<lane>` 六条泳道并行，各自的测试数据库端口不同。

## 2 跑法与输出

docker run -d --name aihot-pg -p 5433:5432 -e POSTGRES_USER=aihot \
  -e POSTGRES_PASSWORD=aihot -e POSTGRES_DB=aihot_test postgres:17-alpine

# 后端套件（在 ../.wt-dev 里，分支 dev）
export DATABASE_URL="postgres://aihot:aihot@127.0.0.1:5433/aihot_dev_ci"
node scripts/migrate.ts && node scripts/seed.ts --topics-only

## 3 后端套件的已知红

`npm test` 的失败测试名固定是这 8 个，与本地修改无关，原因写在 FORK-CHANGES 的「本地测试基线」：
5 个 `SIGTERM` 用例（Windows 上没有 POSIX 信号，子进程被直接终止，测试等到超时）+ 3 个 `tests/translate.test.ts` 用例（打桩 provider 的并发行为在这台机器上不稳定）。
**判断有没有引入回归要比对失败测试的名字，不是看红绿数量。** 这 8 个必须在 Linux 的 CI（`.github/workflows/check.yml`）上跑绿才算过。

本次验收过程中新发现并修掉的两个「看起来像回归、其实是本地可运行性」问题：

1. `apps/web/server.ts` 用 `await import(<Windows 绝对路径>)` 载入 SSR 产物，ESM loader 把盘符当成协议（`Received protocol 'c:'`）拒绝，生产 web 服务在这台机器上一启动就崩，连带 `apps/web/tests/cache.test.ts` 的 9 个用例全红。改成 `pathToFileURL(...).href`。
2. `tests/feishu-projection.test.ts` 假设门户是空的，而测试文件共用一个库，`tests/publication*.test.ts`、`tests/reports-feed.test.ts` 留下的入选条目会一起进投影，于是「这次新建了几行」的绝对计数变成 22。现在每轮先 `settle()` 投影一次再清零发送记录，计数只代表本文件刚发布的东西。
3. 同一个文件还踩了第二道闸门：`selected_ledger.visible_at`。台账里只要有一条还在未来的行，可见前沿就停在那儿，排在它后面的条目（包括本文件自己刚发布的那条）一律读不到，投影于是报「什么都没要发」。现在每轮清掉指向已删文章的台账行，并把还在未来的放行。

**库里跨轮残留会造出假红。** 同一个复用库连跑两次全量套件，第二次多红了 `tests/events.test.ts` 的「two stories stay apart…」；单独在全新库（`CREATE DATABASE` + `migrate` + `seed --topics-only`）跑那个文件是 10/10，全量套件在全新库（`aihot_stage1_test`）重跑也只剩那 8 个。认基线之前先确认库是新建的——CI 每次用的就是现迁的库；否则该排查的是残留，不是改代码。

## 4 站点实看

空库跑一遍之后，再用 `.data/portal-fixture.ts`（试用脚本，走 `upsertMaterial` + 分析行 + `publishArticle` 的真实写入路径，不发模型请求、不采集；`--clean` 删干净）造 5 条演示条目，标着「（演示数据）」，看有内容时的样子：

- 首页信息流出现这 5 条，来源名是包里的真实信源名：**国家标准全文公开系统 · 汽车**、**工业和信息化部 · 政策文件（汽车）**、**Euro NCAP News**。
- 顶部筛选栏是车载分类：法律法规 / 行业标准 / 新车发布 / 技术落地 / NCAP 评测 / 客户动态（`?category=regulation` 等）。
- 标签筛选可用：`/all?tag=DMS` 只剩那条 DMS，`/all?category=ncap` 只剩测评那条。
- 条目页显示来源、摘要、推荐理由与「原文链接」，机制披露字样保留（`AI 评分`、`AI 导读`）。
- `/weekly` 的标题与空状态：`<title>车载周报 · RegWatch</title>`、「还没有发布车载周报」——词从 `industry/site.ts` 的 `subject` 来，不再是「AI 周报」。
- 有内容时 `node scripts/smoke.ts` 仍然 35 项全过。
- 飞书投影在开关关闭、库里 5 条的情况下：`{"status":"disabled","portal":5,"created":5,"updated":0,"unchanged":0,"withdrawn":0}`，一次 HTTP 都不发。
- `llms.txt` 只有在真的出过日报/周报/月报之后才列对应端点（`hasDailies`/`hasWeekly` 决定），空库时不列是预期行为，不是漏配。
- `/api/v1/reports/weekly` 在没有期次时返回 `{"schemaVersion":1,"kind":"weekly","count":0,"items":[]}`。

报头字（nameplate）只能验到「按包里的 `subject` 重新生成」这一步：报告页要有真实期次才渲染报头。演示数据不足以让周报页出报头，所以这一项目前是脚本层面的验证，人眼确认要等有第一期周报。
试用数据看完就清：`node --env-file=.env .data/portal-fixture.ts --clean`。

## 5 回滚实测

实施方案写的阶段一回滚是「`industry/` 包恢复上游默认值 + 信源 `enabled=false`，核心管线未改动，回滚是纯配置操作」。实测了一次（在一条一次性分支上 `git checkout main -- industry` 再 `npm run typecheck`）：

- **回滚到本仓库自己的 `industry/` 包（dev 上那份车载包）确实是纯配置操作**，`git checkout dev -- industry/` 之后类型检查、构建、站点都正常，把 `sources.enabled` 置 false 即可停止采集。
- **回滚到上游示例包不是**：`packages/backend/src/publication/items.ts` 读 `PUBLIC_CATEGORY_FOLDS`（1.3 加进包契约的导出），上游示例包没有这个成员，`tsc -p packages/backend` 直接报 `has no exported member 'PUBLIC_CATEGORY_FOLDS'`；`tests/industry-pack.test.ts` 同理。要把包整个退回上游示例，得连 1.2/1.3 引入的包契约一起退，那不是纯配置。

结论：把回滚目标写清楚——**是 `dev` 上的车载包，不是上游示例包**。实测用的分支已删除，工作树没有留下改动。

## 8 审计中发现但还没补的覆盖缺口

`POST /api/ingest/items`（`packages/backend/src/ingest/items.ts` + `apps/api/src/routes/ingest.ts`）**没有任何测试覆盖**。
1.4 的「需真实浏览器的信源做成外部推送器」和阶段三的原文推送都走这扇门，而它身上带的规则恰恰是最不该悄悄坏掉的那类：token 为空或是占位串时拒绝一切、未知信源一律建成 `kind='external'` + `participation_mode='isolated'`（这是「零新增 kind」的边界）、同一 URL 二次推送不得产生第二篇、旧日期算 backfill 不算今天的新闻、超过 1 小时的未来日期不信但把原话留在 `published_at_claim`、一次超过 50 条整批 413。
测试草稿已写好（`tests/ingest-push.test.ts`，五个用例，全程本地 `app.inject` + 数据库，不出网），落盘同样被拦下等授权。
