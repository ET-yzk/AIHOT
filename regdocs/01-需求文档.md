## 1 背景与定位

### 1.1 一句话定位

以 AIHOT 开源项目为底座，构建覆盖**车载行业动态 + 法规监控 + 原文库 + 解读对比 + 智能问答**的一站式知识平台，服务全公司车载相关部门。

### 1.2 业务动因

ArcSoft 是计算机视觉算法软件供应商，车载业务（驾驶员监测 DMS、乘员监测 OMS、座舱感知、ADAS 视觉感知、车载摄像头数据合规、汽车软件与算法质量）直接受国内外法规与测评规程约束，同时也需要跟踪行业技术落地与新车发布。这类信息有三个特点：

1. **变化频繁且有明确时间节点**：征求意见稿 → 报批 → 正式发布 → 实施，错过一次征求意见或错判实施日期，直接影响立项与排期。
2. **分布极散**：工信部、全国汽标委、市场监管总局、UNECE/WP.29、Euro NCAP、C-NCAP、IVISTA、中汽中心……每个渠道的发布形式、技术形态（RSS / SPA / 反爬门户）、语言都不同。
3. **信息密度极低**：一个渠道一天几十条，与车载视觉真正相关的常常是 0–2 条。人工盯不住，机器粗筛又会漏。

除法规外，以下信息同样需要持续跟踪：新车发布（尤其搭载 DMS/OMS/ADAS 的车型）、车载传感与芯片技术落地、NCAP 评测结果发布、客户（整车厂）的技术动态与合作公告。这些信息与法规动态共享同一套采集与筛选管线，但在热点排序中权重不同。

## 3 用户角色与使用场景

### 3.1 角色矩阵

| 角色 | 关心的问题 | 需要的能力 | 主要触点 |
|---|---|---|---|
| **QA（主要用户）** | 这条法规条款对应的测试依据是什么？要跑哪些用例？现在合规吗？ | 条款→测试依据→用例→合规结论；版本差异对测试项的影响 | 门户法规详情页、对比页、问答、小报 |
| **算法** | 法规对 DMS/疲劳/分心/OMS 等算法模块提出了什么要求？量化指标是什么？ | 按算法标签检索法规、要求条目、生效时间 | 门户检索与专题、问答 |
| **集成** | 法规对应哪些功能与接口要求？整车厂客户提的这条要求出处在哪？ | 按业务分类/适用车型检索，接口级要求抽取 | 门户检索、问答 |
| **认证 / 产品** | 法规体系全景是什么？哪些强制、哪些推荐？下一个认证窗口要按哪一版？ | 生命周期全景、倒计时、认证类型、跨机构对比 | 门户全景页、周报、问答 |
| **法规负责人（当前为 1 人）** | 今天有什么新的要我看？我上次说过的结论还在吗？ | 待评审清单、深读详情、一键收录/暂不关注 | 飞书单聊对话、门户评审队列 |
| **普通读者** | 最近车载行业有什么大事？新车发布、技术落地、NCAP 结果 | 行业动态浏览、按标签筛选（只看法规/只看 NCAP/只看新车等） | 门户首页、小报 |
| **平台运维** | 采集还在跑吗？花了多少钱？ | 运行可观测、成本核算 | 门户管理区 |

### 3.2 核心使用场景（作为验收依据）

- **S-C1 每日哨兵**：早上 8 点，读者在小报里 30 秒看完"昨天有没有我要关心的行业动态"；法规待评审项不在此出现，只在单聊里以深读卡片提醒。
- **S-C2 标签筛选**：读者在门户首页选择"只看法律法规"，页面只显示法规相关动态；切换为"全部行业"则显示所有内容（含新车发布、技术落地等）。
- **S-C3 一句话问到有依据的答案**：QA 问"UN R155 对软件更新管理体系的要求是什么"，得到带条款出处与原文页码的回答，点击可跳到法规详情页与原文定位处；无依据时明确回答"未发现"。
- **S-C4 版本差异影响分析**：某强标发布 2026 版，QA 需要"相对 2024 版新增/修改/删除了哪些试验项"，用于评估测试计划变更。
- **S-C5 全景与倒计时**：产品在做明年规划时，需要"2027 年将实施的核心强标清单"和"90 天内到期的实施日期"，并能按业务分类筛选。
- **S-C6 评审闭环**：负责人在小报/单聊里回复"第 3 条收录"，系统立刻把它从待评审移出、置为高频监控，并把结论落到该法规的决策记录。
- **S-C7 原文自助入库**：认证工程师把手上的法规 PDF 上传到门户，系统完成解析、与法规记录关联、进入可被问答引用的知识层。
- **S-C8 不被打扰**：与车载视觉无关的内容（动力电池、制动、车灯、排放……）不出现在任何面向读者的产物里，且这个"不出现在"是**可查询、可追溯、可撤销**的。
- **S-C9 法规权重优先**：在热点排序中，法规动态（尤其正式发布、实施日期临近）排在一般行业动态之前。

## 6 业务规则（BR）— 重构必须原样保留的资产

> 每条规则背后都是一次返工或事故。完整溯源见 `附录A`。

### 6.1 相关性判定

- **BR-01 三层判定**：一条动态必须**同时**满足 ① 车载行业相关（用于道路机动车的整车 / 系统 / 零部件 / 软件 / 试验方法）② 含软件系统（电子控制 / 软件 / 算法 / 通信 / 数据记录）③ 与公司业务相关（计算机视觉算法供应商视角：DMS、OMS、座舱感知、ADAS 视觉感知、车载摄像头数据安全/隐私、汽车软件与算法质量、智能座舱交互）。三层全满足才纳入。
  - **含**："整车安全类强制性标准中含软件 / 电子控制 / 摄像头 / 数据记录条款的"——客户的合规上游，必须跟。
  - **排除清单（明确不纳入）**：动力三电、底盘机械与电控、车身附件、导航定位硬件、充电设施、传感器硬件、材料工艺、排放环保、工业车辆 / 电动自行车 / 摩托车。
  - **判定方式**：初筛要宽（不得按标题关键词预判过滤），判定交给理解层；三层必须逐层留痕。
  - *事故来源*：2026-09-07 定版；此前"电鸣乐器 GB/T 25454""人居环境 GB/T 27963"被误落表。
- **BR-02 法规落表范围**：只有法规动态（征求意见稿 / 报批稿 / 正式发布 / 首个认证发布 / 法规更新）进入法规追踪；一般行业动态跳过，不得污染法规列表。

### 6.2 生命周期与状态机

- **BR-03 六状态、只进不退**：起草中 → 征求意见稿 → 报批稿 → 正式发布 → 已修订 → 已废止。禁止回退。
- **BR-04 条件必填**：正式发布 ⇒ 发布日期必填；征求意见稿 ⇒ 征求意见截止日期必填；已修订 ⇒ 修订日期必填。
- **BR-05 术语对齐**："法规正式发布"事件 ⇒ 状态"正式发布"；"法规更新"事件 ⇒ 状态"已修订"并必填修订日期。
- **BR-06 日期规范**：一律 ISO `YYYY-MM-DD`；**官方只有月精度时留空，不得填 01 伪造精度**；解析不到就留空。

### 6.3 法规族与子项

- **BR-07 归族判据一（编号基干延续）**：编号去掉版本标识后基干相同 ⇒ 同族。
- **BR-08 归族判据二（官方替代语义）**：官方明确"代替 XX" ⇒ 同族；并列发布 ⇒ 不同族。
- **BR-09 NCAP 代际特例**：Euro NCAP 2023 与 2026 是**并列的规程代际** ⇒ **不同族**。
- **BR-10 子项不单独追踪**：若已存在体系主记录，子项不新增独立记录。判定必须三态（确认子项 / 不确定 / 非子项）。
  - 子项标识匹配必须带词边界（防 `VAN`/`TPMS`/`SMART` 误吞）。
  - 体系前缀匹配必须最长优先（防 `ASEANCAP` 被 `ANCAP` 抢先）。
  - ISO 特例：前缀是 ISO 但编号不是 `ISO <数字>-<数字>` 形式 ⇒ 判非子项。

### 6.4 写入守卫

- **BR-11 只补不删 / 完善不覆盖**：更新已有记录只能填空字段或修正错误值。
- **BR-12 精度不得降级**：月精度不得覆盖已有的精确到日的日期。
- **BR-13 官方链接不得被转载页覆盖**：原文链接已有值时永不写入源表链接。
- **BR-14 零差异即零写入**：无任何差异则完全不发起写操作。
- **BR-15 应填尽填**：新增记录时能填的字段全部填。
- **BR-16 落表即检查**：新增或更新时把"上次检查日期"置为当天。
- **BR-17 黑名单优先且失败即中止**：读取排除清单失败时整个流程中止。
- **BR-18 订阅状态受保护**：一旦被人工设定，自动流程不得改回待评审。

### 6.5 反幻觉与来源可信

- **BR-19 反幻觉三件套**：① 提示词铁律（URL 原样返回）② 代码无条件覆盖（模型给的 URL 一律丢弃）③ 实体一致性守卫。
- **BR-20 宁缺毋滥**：只报告有实际来源支撑的动态；无结果如实写"未发现"。
- **BR-21 先查自有资产**：解读 / 问答 / review 的第一步是查本地原文库 + 知识层，命中即用。
- **BR-22 信源分级与印证**：T1 出现即采信；T2 单源标待印证；T3 仅作线索、**不单独成文**。（2026-10-10 第一次落进代码，只落了「采信」那一半：`publication/corroboration.ts` 的一个谓词，热点榜与日报的漏选补位都读它，权威层名单由包声明（`industry/selection.ts` 的 `corroboration.authoritativeTiers`，今天只列 T1）。**「标待印证」与「T3 不单独成文」两半仍未做**：三态标记没有任何出口要（读者侧按 FR-02-06 不印状态），`EXCLUDE_MP` 今天只挡精选、仍进 `/all` 与主题页，挡到哪一层与 T1/T2/T3↔`T1/T1_5/T2/EXCLUDE_MP` 的映射一起等使用者定（交接页第 18 条与验收记录 §28.1）。

### 6.6 表达规范

- **BR-23 全文中文**；解读引用必须带链接 + 页码。
- **BR-24 禁套话**：值得注意的是 / 据悉 / 旨在 / 此外 / 进一步 / 加强完善。
- **BR-25 面向读者重写**：写"法规本身变了什么、影响是什么"的人话，不得出现内部管理表述。
- **BR-26 名称列必须带编号**：`[编号 《全称》](真实URL)`。
- **BR-27 表格转义**：Markdown 表格内管道符必须转义。
- **BR-28 卡片单一生成器**：投递卡片只能由唯一渲染器生成。

### 6.7 归档与文件归位

- **BR-29 归档契约**：原始数据与解析后数据必须归档。
- **BR-30 文件归位**：工具包 → 运行数据目录；报告 → 输出目录；**禁止散落**。

## 8 非功能需求

### 8.1 规模基线

| 维度 | 现状 | 设计余量 |
|---|---|---|

| 法规追踪数 | 约 73 条 | 数千条 |
| 原文库 | 约 69 条索引 | 逐年增长 |

### 8.2 外部环境约束（硬）

- **上游模型服务限额**：内部 OpenAI 兼容网关，**40 请求/分钟、5 并发**。所有调用方共享此额度。
- **单机资源**：内存 7 GB、无 GPU。重负载组件不得与本系统同机共存。
- **网络**：知识层服务在局域网另一主机；信源在公网；企业 IM 为外部 SaaS。

### 8.3 正确性

- 幂等：任何一次重放都不得产生第二条记录或第二次计费。
- 可追溯：每个结论能回答"依据是什么、谁或什么在什么时候做的"。
- 一致性：一个内容在所有出口上的表述与可见性必须一致。
- 人工优先：人工判断永远优先于自动判断，且不被后续自动流程覆盖。

### 8.4 可运维性

自检前置、预算与配额可在线调整、信源可独立试抓与调频、失败可分类批量重跑。

### 8.5 安全

- 秘密不入库、不进日志、不出现在任何产物里；上游令牌不得硬编码。
- 服务端外访必须默认拒绝内网地址，对确需访问的内网服务用窄口径白名单。
- 从公网抓来的内容进入模型前必须被视为不可信数据。

### 8.6 成本

每次模型与外部服务调用可核算到钱；日均与月度成本可见；预算为熔断器。

### 8.7 与上游 AIHOT 的兼容

- **核心原则**：对 AIHOT 核心代码的改动最小化，优先通过 `industry/` 包注入领域配置。
- **必须修改的**：industry/ 包内容（信源、分类、提示词、筛选规则）。
- **尽量不改的**：`packages/backend/src/` 核心管线代码。
- **如果必须改核心**：改动必须是追加式的（新模块、新端点），不改动既有函数签名与数据流，以保证上游更新可合并。
- **删除的**：AIHOT 自带的模型榜单与订阅额度监控两个模块（属于另一个行业，在派生时关闭或删除）。

## 9 现状问题清单

### 9.1 定时任务因框架依赖崩掉

早间任务 `last_status = error`：外部 worker 在导入链中 `ModuleNotFoundError: No module named 'ruamel'`。**根因是两套 Python 世界互踩**。迁移到 AIHOT（TypeScript 统一运行时）后此问题自然消除。

### 9.2 业务规则不可测试

三层判定、卡片格式、状态机、归族判据都写在提示词里，规则改了没有回归验证。迁移后，BR-01..BR-30 必须成为可执行的测试断言（见 `附录A`）。

### 9.3 事实层无事务、无历史

状态机与条件必填靠写入前校验；跨字段约束无法在存储层保证。AIHOT 的 Postgres 提供了事务能力，法规模块的写入守卫可在数据库层强制。

### 9.4 秘密与硬编码

多处硬编码表 ID、空间 ID、会话 ID、绝对路径与令牌。迁移时一律作为**待撤销的秘密**处理（视为已泄露），配置外置且集中。

### 9.5 契约与实现双源

契约声明的爬取源清单没有任何代码去读；实际生产的通道不在契约里。迁移后，信源注册表（`industry/sources.json`）是**唯一**配置源。

### 9.6 历史记忆的随机遗忘

URL 去重记忆按字典序截断。AIHOT 的 `articles` 身份机制基于内容哈希，不存在此问题。

### 9.7 交付链路对单一聊天工具的强耦合

小报、群发、wiki 归档全依赖企业 IM。AIHOT 已有门户与 API/RSS 出口，迁移后自然解除。

## 10 范围外

明确不做，避免范围蔓延：

1. 不做模型训练/微调；只使用既有网关模型。
2. 不做公开互联网可访问的站点（内网定位）。
3. 不在阶段一实现测试用例生成与报告分析（只预留接口）。
4. 不做法规条款级的全量结构化录入（条款正文由原文与解读承载）。
5. 不做多维表格的双向同步（飞书表降为只读视图或完全由门户取代）。
6. 不沿用 AIHOT 自带的模型榜单与订阅额度监控模块。
7. 不在本次重构中更换向量模型或重建知识层分区。
8. 不在阶段一实现完整的 RBAC（先做企业身份登录 + 基础角色，细粒度权限后续迭代）。
